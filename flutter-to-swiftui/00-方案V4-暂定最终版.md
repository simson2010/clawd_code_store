# Flutter App → SwiftUI 原生重写：落地方案（暂定最终版 V4）

> **本文是唯一事实源。** 由 V1（评审）→ V2（六条补充）→ V3（终版）→ V3.1（组件库就绪）四轮迭代合并而成，历史版本已移至 `archive/` 仅供溯源，**引用时一律以本文为准**。
> 配套：`templates/screen_spec.md`（屏幕行为契约模板）、`templates/p0_kickoff_checklist.md`（P0 检查清单）、`tools/scan_flutter_widgets.py`（组件扫描器）、`07-给管理层-UI应从Figma生成而非源码推导.md`（对外汇报）。

---

## 1. 一页纸摘要

**做什么**：把现有 Flutter App（有源码、有 Figma）用 AI Agent 辅助重写为 Swift + SwiftUI 原生 App，Bundle ID 相同直接覆盖上架。

**怎么分工**（整条方案的核心）：

| 层 | 负责方 | 产出性质 |
|---|---|---|
| UI + TCA 骨架 | **GenUI**（Figma → 代码，已绑定内部组件库 + TCA） | **可再生**：改稿就重新生成 |
| Reducer 业务逻辑 | **AI Agent**（读 Dart 提取的 Screen Spec） | **持久**：手写一次，长期维护 |

**三个绝不动摇的工程决策**：

1. **文件所有权隔离**：GenUI 产物与手写逻辑物理分文件 + CI 守护，否则第二次设计改稿就会吃掉业务逻辑。
2. **Spec 墙**：Agent 之间用与语言无关的 Screen Spec 传递，实现侧 Agent 禁止读 Dart 源码，杜绝"Dart 味的 Swift"。
3. **数据迁移预埋导出**：在 Flutter 倒数第二个版本加一次性 JSON 导出，Native 首启读取转换 —— 有提前量，**现在就要排期**。

**最大剩余风险**：数据迁移失败（用户可感知）、组件库缺口/版本升级连带（依赖风险）、埋点口径漂移（静默失败）。

## 2. 已确认前提（不再讨论，作为方案地基）

| # | 前提 | 对方案的意义 |
|---|---|---|
| ① | 新 App 纯 SwiftUI Native，Flutter 代码全部丢弃；套用现有原生壳 | 无 Flutter module 双跑架构；壳要做可继承度体检（§5.10） |

| ④ | Flutter 版**会先推向 C 端**，之后 Native 覆盖 | 数据迁移、埋点对齐、服务端兼容**全部要做** |

| ⑥ | 网络层复用**自建网络库** | DomainModel SDK 职责收窄（§5.3） |

| ⑨ | **内部组件库完备，双平台，线上其它 App 在用** | P1 硬阻塞消失，但引入依赖治理问题（§5.1） |

**分工总原则**：视觉以 Figma 为准（GenUI 消费），行为以 Dart 源码为准（Spec 提取），两者在 Screen Spec 汇合。

## 3. 总体架构：可再生层 vs 持久层

### 3.1 为什么这是头号工程决策

GenUI 会**反复重新生成**。如果它的输出与手写 Reducer 逻辑混在同一文件，第二次设计改稿就会灾难性地覆盖业务逻辑。组件库再完备也不解决这个问题 —— 这是 GenUI 输出格式与手写逻辑的关系问题。

### 3.2 文件所有权矩阵

| 文件 | 生成方 | GenUI 可否覆盖 | 内容 |
|---|---|---|---|
| `XxxView.swift` | GenUI | ✅ 随时覆盖 | 纯渲染，只读 ViewState |
| `XxxViewState.swift` | GenUI | ✅ | UI 展示字段 |
| `XxxViewAction.swift` | GenUI | ✅ | 来自 UI 的点击/输入 Action |
| `XxxDomainState.swift` | Agent / 人 | ❌ 永不覆盖 | 真实业务状态机（来自 Dart Spec） |
| `XxxDomainAction.swift` | Agent / 人 | ❌ | API 结果、业务事件 |
| `XxxLogic.swift` | Agent / 人 | ❌ | Reducer 主体、Effect、依赖调用 |
| `XxxFeature.swift` | Agent / 人 | ❌ | 组合 reducer |

**CI 守护**：GenUI 输出目录出现 ❌ 类文件直接报错，要有自动化测试，不靠口头约定。

**免费红利**：GenUI 重新生成导致 ViewAction/ViewState 签名变化时，❌ 层**编译失败** —— 编译器就是变更检测器。团队约定：**编译错误 = 设计发生结构性变更，按错误信息修逻辑层**，而不是随手改名让它编译过。

### 3.3 三层 State 分离

GenUI 生成的 State 是朴素的（`isLoading` + 数据），Spec 提取的真实状态机丰富得多（空/错/离线/无权限/部分失败/加载更多）。不要 merge，要分层：

```swift
struct XxxState {
    var view: XxxViewState        // GenUI 生成，可再生
    var domain: XxxDomainState    // 手写，持久 —— 真实状态机在这里
}
```

View 只读 `state.view`；Reducer 驱动 `state.domain` 再投影到 `state.view`。**GenUI 永远不知道 `domain` 存在，也就不可能破坏它。**

### 3.4 视图层的两层拆分

```
XxxFeature (TCA)            ← Agent 写：状态机 + 副作用
   ├── XxxViewState         ← 纯数据，View 只认这个
   └── XxxLayout (SwiftUI)  ← GenUI 产物落这里：纯渲染、零 @State
```

Layout 是纯函数式渲染层。GenUI 结构 100% 复用，只需把字面量替换为 `state.xxx` —— 机械变换，Agent 做可靠，人做无聊。

## 4. Agent 产线

### 4.1 Spec 墙（不可省略）

```
Analyzer Agent（只读 Dart + 抓包 + 录屏，禁止写 Swift）
        ↓ 产出 Screen Spec（templates/screen_spec.md）
   ── 规 约 墙 ──
        ↓ 只读 Spec
Implementer Agent（禁止读 Dart）
```

让实现 Agent 直接读 Dart，必然生成"Dart 味的 Swift"（`_buildBody()` 命名、深层嵌套、setState 思维）。Spec 是唯一切断污染的手段。

### 4.2 四个输入源（单靠读代码不够）

| 源 | 提供什么 | 优先级 |
|---|---|---|
| **真机抓包**（Charles/mitmproxy 跑 Flutter App） | 后端**实际**契约：分页参数、错误码、字段可选性 | 最高 —— 代码写的是"开发者以为的契约" |
| **真机录屏**（每屏一段操作视频） | 转场动画、状态切换 —— 代码和 Figma 里都没有 | 高 |
| Dart 源码 | 结构、意图、业务规则 | 高 |
| Figma | 视觉与 token（经 GenUI） | 视觉唯一权威 |

### 4.3 Screen Spec 要点

模板见 `templates/screen_spec.md`（14 节，每节必填，空项写 N/A）。**"状态机"和"并发"两节是 Agent 最高频遗漏项**，prompt 里必须点名要求并给反例。埋点节已拆为 10.1 行为 / 10.2 曝光 / 10.3 时长三段，行为埋点必须填"上下文来源字段（State 路径）"列 —— 这是自动埋点中间件取参的依据。

### 4.4 上下文切片（大仓库必做）

1. 从入口路由构建文件依赖图；2. 每屏取 N 跳内可达文件（N=2 通常够）；3. 公共层（theme/network/utils）用摘要而非全文；4. 先跑 `tools/scan_flutter_widgets.py` 出组件清单当 Agent 的"地图"。

### 4.5 角色编排

| 角色 | 输入 | 输出 | 硬约束 |
|---|---|---|---|
| Analyzer | Dart + 抓包 + 录屏 | Screen Spec | 禁止写 Swift |
| SDK Builder | API 契约 | Domain SDK + Mock | 禁止引用 View |
| Layout Producer | Figma（经 GenUI）+ Spec 视觉节 | XxxLayout.swift | 禁止写状态逻辑 |
| Feature Builder | Spec + SDK + GoldenExamples | XxxFeature.swift | 禁止读 Dart |
| Reviewer | 产物 + Spec + lint 规则 | 编译结果 + Parity 报告 | 过门禁才合并 |

### 4.6 GoldenExamples 语料库（全线 ROI 最高的投入）

已有线上 App 在用同一套组件库 + TCA —— 公司里已存在几十上百个**符合规范的 Feature 实现**，这是 Agent 最好的 few-shot 素材：

| 做法 | 收益 |
|---|---|
| 抽 20–30 个内部 Feature 建 `GoldenExamples/` | Agent 填 Reducer 时模仿而非创作 |
| 提炼命名约定、Effect 写法、错误处理、依赖注册、测试写法 → `AGENT_RULES.md` | 变成 prompt 硬约束 |
| 内部 lint / 架构规则接入 Reviewer Agent | 自动校验，减人工 review |
| 拿带测试的 Feature 生成 `TestStore` 测试范式 | Reducer 单测有模板 |

**P0 第一周做，1 人 3 天。前提是能读到其它线上 App 源码 —— 尽早开口。**

## 5. 各子系统方案

### 5.1 组件库治理（共享依赖的代价）

组件库完备消灭了建设风险，但引入**依赖风险** —— 看不见、加班解决不了、优先级不在我们手上。需要治理而不是加班：

| 风险 | 对策 |
|---|---|
| **R1 版本升级连带破坏**（库为其它 App 演进，无声改掉你的视觉） | 锁版本 + 显式升级（禁止跟 main）；**每次升级跑组件 snapshot 回归**；订阅 changelog 纳入发版评审。若库有 preview catalog/Demo App，直接拿来做 baseline |
| **R2 需求排队**（"完备"是对现有 App，你的缺口在别人节奏里） | P0 立即产出「库有 / 库缺 / 语义不同」三态缺口清单，尽早提需；**越晚提越卡 P4** |
| **R3 双平台一致性约束**（只改 iOS 侧通常不被允许） | P0 盘点 iOS 特化点（系统分享、长按菜单、Haptic、原生导航语义），能内置交库，不能的在 **App 级适配层**做 |
| **R4 同名不同义**（名字一样语义不同，最晚炸） | 缺口清单里单列一类重点核对 |
| **R5 既定规范的服从成本** | 不另起一套，把现有 App 的 TCA 集成、@Dependency 注册、错误处理、测试写法抄成 Agent 硬约束 |
| **R6 Bug 修复 SLA 不在你手上** | P0 建协作机制（对口人、响应时长）；适配层预留 hotfix 包装能力；列出你依赖的高风险组件请对方重点保障 |

**硬规则：本地禁止 fork 组件库。** 优先级：扩展配置 → 提需求 → 本地薄包装。一旦有人 fork，版本治理立刻失效。

**App 级组件适配层**（业务页不裸调库组件）是 R3/R6 共同的阀门，也是灰度切换、埋点节流收口的唯一位置：

```swift
// 全 App 唯一依赖 DS 的地方
struct AppButton: View {
    var body: some View {
        DSButton(title: title, style: map(variant), isBusy: isLoading) {
            Analytics.track("button_tap", ["title": title])   // 行为层在这里补齐
            action()
        }
    }
}
```

落地顺序：先建空壳（转发系统组件）让全项目编译过 → 逐个换 DS 组件（一个 PR 一个）→ 每个配 #Preview 四态对照。

### 5.2 Design Token

库已完备 ⇒ Token 体系大概率已存在，**确认并复用，别重建**。需要核实的只有三点：输入源（Figma Variables？独立仓库？）、语义化命名（禁止 `blueLight`/`blueDark` 值级命名，视图代码明暗模式必须一致）、CI 契约测试（每平台产物 token 齐全 + 禁止手改生成文件）。

### 5.3 DomainModel SDK（职责收窄）

```
自建网络库（传输、拦截、鉴权、Token 刷新）
        ↓
  Repository 实现层      ← 复用网络库发请求
        ↓
  DTO ⇄ Domain Mapping   ← SDK 核心，真正要新建的部分
        ↓
  Domain Model（Sendable 值类型、含业务不变量）
        ↓
  AppError 分类（不是裸网络错误）→ View 层只认这个枚举
        ↓
  Mock 实现（同 protocol，先于真实实现交付）
```

**网络库四项能力盘点**（缺哪块 SDK 补哪块）：async/await 接口、**请求取消**（页面退出后响应改写已销毁 State）、**Token 刷新并发合并**（多 401 打爆后端）、mock 能力。另确认**是否 Swift 6 / Sendable ready** —— 决定全项目开不开 Swift 6 language mode，要早定。

**六条硬规则**：DTO 与 Domain 分离；先出 Mock；契约来源优先级 OpenAPI > 抓包 > 读 Dart；重试/幂等/取消/竞态收口在 SDK 层（含幂等键、后发先至防覆盖）；错误分类枚举；按屏幕需要增量做，不大爆炸交付。

### 5.4 TCA 策略

值得上，核心理由不是"架构好看"：`State` 穷举补 Flutter 隐含状态机、`Effect` 显式补行为层、`@Dependency` 让 SDK 可注入可 Mock —— 三个特性正好对准本项目三个难点。

**但不全量上**：有状态机/副作用/多步流程的屏用 TCA；纯展示 + 单请求用 `ObservableObject` + ViewModel；纯静态直接 SwiftUI。全量会把简单页成本抬高 2–3 倍。注意 iOS 16 下 TCA 的 `@ObservableState` 依赖 Perception 回移植，样板略多，试点屏先验证。

### 5.5 路由（自定义 NavigationStack 的五个隐藏坑）

1. **NavigationPath 的 Codable 版本兼容** —— 路由枚举改字段，旧用户存的 path 解码失败会崩。每个路由加版本号 + 解码失败降级到首页。
2. **深链冷启动重建整条路由栈** —— 最常见线上崩溃点。
3. **返回值传递** —— 无 delegate，用 @Binding / 路径回调，写进 Spec 导航节。
4. **路由守卫** —— 未登录拦截在路由层统一做。
5. **自定义导航栏与 swipe-back 手势** —— interactivePop 易失效或卡死。

### 5.6 埋点（TCA 自动埋点的四个硬边界）

高阶 Reducer 拦 Action → 映射事件，思路正确，是 TCA 独有能力。但：

| 边界 | 问题 | 对策 |
|---|---|---|
| ① Action 粒度 ≠ 事件粒度 | 一次点击触发 Action 链，重复上报 | 白名单（`TrackableAction`）+ 300ms 去重窗口 |
| ② Action 里缺埋点上下文 | 商品 ID、来源页、坑位、实验分组不在 Action 里 | **中间件从 State 快照取**（不污染 Action 定义）；Spec 埋点节"上下文来源字段"列保证可达 |
| ③ 曝光埋点 Redux 覆盖不到 | "露出 50% 持续 1 秒"是 View 层可见性判定 | **独立通道**：PreferenceKey / 自建曝光容器；页面时长同理 |
| ④ 事件模型漂移 | Tagging 文档改了代码没跟上 | 从 Tagging 文档生成 Swift 枚举 + CI diff；代码禁止字面量事件名；预留服务端采样率/黑名单下发 |

**因 ④（Flutter 先上 C 端）追加三条**：从 Dart 提取全量事件清单建 Flutter ↔ Tagging ↔ Native 三方映射；**CI 断言 Native 实现集合 == 映射表**；上线后双端埋点并行观测期，口径一致再合并看板。自动埋点去重策略若与 Flutter 版不一致，量级会差几倍。

### 5.7 数据迁移（头号用户可感知风险）

**核心策略：Flutter 端预埋导出，别让 Native 猜私有存储格式**（Hive 二进制、sqflite 库表）。在 Flutter **倒数第二个版本**加一次性导出：关键数据序列化为 JSON（带 `version` 字段）写到 App Group 共享位置；Native 首启读取、转换、写库。**导出代码至少提前两个版本带上**，让覆盖面铺够。

迁移内容清单：

| 数据 | Flutter 实现 | iOS 落点 | 方式 |
|---|---|---|---|
| 登录态 / 用户设置 | shared_preferences | UserDefaults（key 前缀 `flutter.`，原生可直接读） | 直接读 |
| 凭证 / Token | flutter_secure_storage | Keychain（同 accessGroup，service/account 一致） | 直接读 |
| 草稿 / 离线数据 / 浏览历史 | sqlite / Hive | 私有文件 | **走导出** |
| **未完成业务状态**（购物车草稿、未提交表单） | 各异 | — | **走导出，最易漏，找产品列清单** |
| 图片 / 文件缓存 | path_provider | 可弃 | — |

**执行六规则**：① 首启同步完成 ② ≤2s 超时降级不卡启动 ③ 幂等（标记位）④ 原子（失败整体回滚可重试，不允许半迁移）⑤ 源数据保留一个版本 ⑥ **迁移结果必须上报埋点**（成功率、失败原因分布 —— 不上报 = 上线后不知道多少人丢数据）。

**验证唯一途径**（进测试用例）：`装 Flutter 最后版本 → 造数据（登录/设置/草稿/历史）→ 覆盖装 Native → 逐项核对`。代码 review 看不出来。

### 5.8 服务端双客户端兼容

Native 上线 ≠ 所有人立刻升级。**Flutter 首发那天就要规划**：请求带 clientType + version header 分流；响应向后兼容（旧客户端对未知枚举常无兜底）；明确最低支持版本与强制更新时间点；灰度不要按 App 版本混看两个客户端的数据。

### 5.9 灰度与回滚

无 Flutter module 双跑，灰度 = **TestFlight 分批 → Phased Release → Kill switch 待命**。

- **Kill switch（服务端功能开关）是首发期唯一急刹车**：App Store 不支持降版本，提审回滚是小时级。出严重问题时服务端下发配置隐藏入口/切 H5。优先复用壳里现成的配置下发通道，没有才新建（用平台方案，不自造）。
- **版本号提前排**：Native 版 > Flutter 最后版；回滚版 > Native 版；Build 号单调递增。
- **覆盖安装保留沙盒**：既是数据迁移前提，也意味着脏数据会跟过来 —— 迁移逻辑要有容错。

### 5.10 原生壳可继承度体检

"复用壳"省事，但壳的技术债会顺着污染新项目。P0 出矩阵（复用 / 替换 / Facade 包装）：

| 壳能力 | 需确认的问题 |
|---|---|
| 网络层 / Token 刷新 | 与 Domain SDK 是否打架？**两套刷新逻辑必炸**，归属二选一 |
| 账号 / 登录态 | 与 Flutter 版是否同一套 SSO |
| 埋点 SDK | 能否承载新 Tagging 方案 |
| 配置下发 | 有没有现成的（Kill switch 直接复用） |
| 崩溃 / 性能监控 | 符号表、版本串是否分开 |
| 推送 | device token、别名/标签是否重建 |
| CI / 打包 / 证书 | 最有价值，通常直接复用 |
| 部署 target / Xcode / Swift 版本 | 壳若低于 iOS 16 需处理；TCA 宏需 Xcode 15+ |

口径：**横切 infra（CI/监控/配置下发）直接复用；业务 infra（网络/账号/路由）重评估**。

### 5.11 UIKit 逃逸通道

纯 SwiftUI ≠ 禁止 UIKit。复杂转场、高性能长列表、地图/相机/网页容器仍需 `UIViewRepresentable`。架构预留槽位，别设"禁止 UIKit"，否则后期会以更丑的方式打破规则。

### 5.12 iOS HIG 重新定性

Flutter 一套代码两端跑，很多设计是"两端凑合"。转原生后按 iOS 规范重新定性：导航栏与返回手势、安全区、键盘避让、动态字体、VoiceOver、长按菜单、系统分享、Haptic。Figma 通常没画这些，靠组件库内置 + 适配层 + 人工抽检兜底。

## 6. 窗口期管理（Flutter 上线 → Native 上线）

这期间 Flutter 仍在迭代，三个连锁问题：Spec 过期、需求重复实现、Native 上线时功能落后。

| 措施 | 做法 |
|---|---|
| 冻结基线 | 选定 Flutter 版本号为 Spec 基线，写进 `SPEC_BASELINE.md` |
| 发版 diff 同步 | Flutter 每次发版 → diff → 更新受影响屏幕 Spec，标 `SPEC_CHANGED` |
| **需求分流** | 窗口期 Flutter 端只做必修（崩溃修复、合规、服务端配合），**新功能一律不做** —— 控制双份成本的唯一办法，**写进项目章程** |
| 窗口期上限 | 硬性时间点（建议 ≤ 6 个月），过期重新评估 |

Flutter 仓库在 Native 上线前**只读归档不删除**，保留真机包作 QA/产品验收参照。

## 7. iOS 16 基线的连锁决策

| iOS 17+ 但用不了 | 替代方案 | 影响面 |
|---|---|---|
| `@Observable` 宏 | `ObservableObject` + `@Published` | 全项目：粒度变粗，更注意 View 拆分 |
| TCA `@ObservableState` | Perception 回移植 / `WithPerceptionTracking` | 样板略多，试点先验证 |
| `SwiftData` | Core Data / GRDB / 文件缓存 | **持久化方案需重定（待决策）** |
| `ContentUnavailableView` | 自建空态组件 | 走组件库，正好覆盖 |
| `.scrollPosition(id:)` | `ScrollViewReader` 手动算 | 滚动定位、分页吸顶手写 |
| `onChange(of:initial:)` 双参 | `onAppear` 手动补首次 | 小坑易漏 |

**iOS 16 红利**（明确利用）：`Charts` 原生图表（Flutter 自绘图表可大幅简化）、`Layout` 协议、`AnyLayout`、`ViewThatFits`、`Grid`、`ShareLink`、`PhotosPicker`。

> iOS 16 这个决定要**数据驱动**：拿目标用户 iOS 版本分布，老板签字，不默认。

## 11. 验收标准

**每屏 Parity Checklist**（由 Spec 自动生成，逐项打勾才允许合并）：状态机全覆盖 / 边界全覆盖 / 埋点事件与参数逐一对齐 / 视觉回归通过（Figma 切图 ↔ snapshot，关键路径加 Flutter 真机对照）/ 无硬编码色值间距 / accessibility（VoiceOver、Dynamic Type、深色）通过 / 单测覆盖状态转换 / TestStore 覆盖主要副作用。

**每组件验收**：四态对齐（默认/加载/空/错误）/ 深色 / Dynamic Type 超大字号 / VoiceOver 焦点与标签 / 埋点事件名与 Flutter 一致 / 截图对比（同设备同数据）。

**GenUI 产物卫生门禁**（CI 机器检查）：禁止色值/hex 字面量（走 Token）；禁止硬编码 frame 尺寸；禁止 position/offset 做布局；可点击元素必有 accessibilityLabel；文本走 LocalizedStringKey；间距必须来自 Spacing token；body 内禁止计算逻辑。

**Figma 侧治理**（GenUI 质量 ≈ Figma 质量）：组件化（重复元素必须是 Component）、全容器 Auto Layout、绑定 Variables 且与 Token 同名、补齐状态变体稿（空/错/加载/超长文本/无图 + 组件 10 态 variant 审计）。

## 附录 A：Flutter → SwiftUI 组件映射速查

> 完整指南（三层拆解、Token 桥、适配层模式、自绘组件）见 `archive/02-组件映射落地指南.md`。**认知前提：映射最小单位是 Modifier 不是 View**；公司自定义组件 90% 的工作量在行为层不在视觉层。

结构层：

| Flutter | SwiftUI | 备注 |
|---|---|---|
| `Column` / `Row` / `Stack` | `VStack` / `HStack` / `ZStack` | spacing 直接对应 |
| `Expanded` / `Flexible` | `Spacer()` / `.frame(maxWidth:)` | 无 flex 系数，用 LayoutPriority / ViewThatFits |
| `ListView.builder` | `List` / `LazyVStack` + ScrollView | 懒加载用 LazyVStack |
| `GridView` | `LazyVGrid` + GridItem | — |
| `Scaffold` + `AppBar` | `NavigationStack` + `.navigationTitle()` + toolbar | — |
| `BottomNavigationBar` | `TabView` | 手势返回行为不同 |
| `showModalBottomSheet` | `.sheet()` + `.presentationDetents()` | iOS 16+ |
| `SnackBar` | 无原生 | 自建 overlay |
| `Hero` | `.matchedGeometryEffect()` | — |
| `NestedScrollView` / `Drawer` | ❌ 无等价 | 需重新设计交互 |

行为层陷阱：`TextEditingController` → `@State`（别存 ViewModel）；`FocusNode` → `@FocusState`；`ScrollController` → `ScrollViewReader`；`RefreshIndicator` → `.refreshable`；`WillPopScope` → iOS 不能拦截，需隐藏返回键 + 自定义。

必须新建（路径 C）：`CustomPainter` → `Canvas`；`CustomClipper` → `Shape`；`BackdropFilter` → `.background(.ultraThinMaterial)`；大面积 GLSL → Metal + `UIViewRepresentable`；三方地图/相机/WebView → 官方 SDK 桥接不重写。
