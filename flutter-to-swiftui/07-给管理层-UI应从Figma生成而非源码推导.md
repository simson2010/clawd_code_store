# 建议：UI 从 Figma + GenUI 生成，而不是由 AI 从 Flutter 源码推导

> **用途**：向管理层说明技术路线选择，用于立项、排期与资源争取。
> **阅读时间**：约 8 分钟。第 1 节为决策摘要，第 6 节为常见质疑应答。

---

## 1. 决策摘要（一页纸）

**建议**：UI 层全部由 GenUI 从 Figma 生成；Flutter 源码只用于提取**业务逻辑**，不作为 UI 的来源。

三个决定性理由：

| # | 理由 | 一句话 |
|---|---|---|
| **1** | **可再生性** | Figma → 代码是**可重复执行**的机器过程；源码推导是**一次性的人工产物**。改一次稿，前者重新生成，后者要重新推一遍 |
| **2** | **源码里没有干净的 UI 意图** | Flutter 源码里混杂着临时 hack、废弃分支、AB 残留、跨端妥协代码。AI 无法分辨哪些是当前有效设计，会把历史债原样搬进新项目 |
| **3** | **这是一次甩掉技术债的机会** | 重写的价值之一就是摆脱历史包袱。如果以旧实现为准，包袱会以更隐蔽的方式保留下来，而且再也没人会去清理 |

**代价**：前期需要投入 GenUI 就绪、Figma 治理与标注规范（约 1–2 人月的准备工作）。
**回收**：在第 2 次设计改稿时收回成本，之后每次改稿的边际成本约为源码推导路线的 **1/5**。

---

## 2. 两条路线的准确定义

先把要比较的东西说清楚，避免讨论时各说各的：

| | **路线 A（建议）** Figma + GenUI | **路线 B** AI 读 Flutter 源码推导 UI |
|---|---|---|
| UI 来源 | Figma 设计稿 | Flutter 源码 widget 树 |
| 产出方式 | 工具生成，可重复执行 | AI 生成一次，之后人工维护 |
| 组件一致性 | 由内部组件库从源头保证 | 依赖 AI 每次都认出该用哪个组件 |
| 改稿成本 | 重新生成 + 少量逻辑适配 | 人工在全量代码中定位并修改 |
| 与设计的偏差 | 结构上不可能（同一份源） | 会累积 |

> **注意**：两条路线**都要**读 Flutter 源码 —— 因为 Figma 不描述业务规则。区别在于源码用来干什么：**A 用它提取业务逻辑，B 用它推导 UI**。这不是"是否利用已有资产"的分歧，是"资产用在哪"的分歧。

---

## 3. 六个论据

### 论据 1：可再生性 —— 决定性的一条

这是工程管理上的分水岭。

**路线 A**：设计改稿 → 重新跑一次 GenUI → UI 自动同步。虽然逻辑层可能需要小幅适配，但**改了哪里一目了然**（重生成的 diff 就是变更清单）。

**路线 B**：设计改稿 → 需要有人（或 AI）在全量已生成的代码里找到所有受影响的位置 → 逐个修改 → **没有任何机制保证找全了**。而且第二次推导的结果和第一次必然不完全一致 —— AI 不是确定性函数。

> 一个直观的类比：路线 A 是**编译**，路线 B 是**手工翻译**。编译可以每天跑，手工翻译每重译一次都会产生新的不一致。

**这条直接决定了项目后期能不能快起来。** 批量生产阶段，设计稿一定会反复调整，这是常态而不是意外。

### 论据 2：Flutter 源码里没有干净的 UI 意图

一个上线运行过的 Flutter 工程，其 UI 代码里必然包含：

| 噪声类型 | AI 能否识别 | 后果 |
|---|---|---|
| `Platform.isIOS ? A : B` 的跨端分支 | 部分能 | 把 Android 分支的逻辑带进 iOS 代码 |
| 已经不生效的 AB 实验残留分支 | **不能** | 死代码被当成有效设计 |
| 注释掉的旧版本实现 | 有时误读 | 生成已废弃的 UI |
| 为绕过某个 Flutter bug 写的 hack | **不能** | SwiftUI 里不存在这个 bug，hack 变成无意义的负担 |
| 设计师没来得及给的临时占位实现 | **不能** | 占位被固化为正式实现 |
| 跨多处拼接的 Theme 覆盖 | 部分能 | 提取出的色值/间距与最新规范不符 |

**AI 无法区分"当前有效的设计"和"历史遗留"。** 它读到什么就复现什么。这意味着以源码为准，等于**把过去两年所有的临时决定固化进新项目**，而且这次固化后，没人知道哪些是历史债。

### 论据 3：Widget 树到视图树的映射是有损变换

这一条偏技术，但它解释了"为什么这件事本质上是逆问题"。

Flutter 的一个 `Container` 同时承担 padding、背景色、圆角、阴影、约束五件事。反过来说，Flutter 源码里一个视觉效果通常散布在嵌套的多层 widget 中：

```
Padding
  └─ DecoratedBox (背景 + 圆角)
      └─ ClipRRect (裁剪)
          └─ BackdropFilter (模糊)     ← 一个视觉效果的四层表达
```

而 SwiftUI 的表达是平的：`View().padding().background().clipShape().background(.ultraThinMaterial)`。

**从"四层嵌套"反推"一个视觉效果 + 参数的组合"，是典型的逆问题** —— 存在多种合理解，AI 只能猜。猜对的时候产出尚可，猜错的时候产出的是"能跑但结构混乱"的代码，而且这种混乱要在几个月后才显现为维护成本。

更麻烦的是，Flutter 的 UI 是**运行时计算**的（Theme 查表、InheritedWidget 跨层传值、响应式布局），纯静态读代码推不出最终效果。

### 论据 4：Flutter 端的视觉是"跨端妥协"的结果

一套代码跑两个平台，很多地方是双方凑合的产物：例如用 Flutter 自己绘制的仿 iOS 导航栏、仿 Cupertino 风格的控件、为了两端都能接受而定的间距。

这些妥协在纯 iOS 原生项目里**既不必要也不可取**。1:1 复刻等于把妥协带过来，用户拿到的是"像 iOS 但不完全是"的体验。

### 论据 5：Figma 是可验收的单一事实源

工程管理角度，这一条非常重要：

- **Figma 可以评审** —— 产品、设计、开发看的是同一份东西，验收标准明确
- **Figma 可以 diff** —— 改了什么一目了然
- **GenUI 的输出可被验证** —— 同一份 Figma 生成两次结果应当一致，这是可测试的性质

而"AI 从源码推导的结果"没有客观对错标准，验收时只能靠人眼比对，**评审成本反而更高**。

### 论据 6：GenUI 已绑定内部组件库与 TCA —— 路线 A 的前置条件已经具备

这一点让建议变得更实际：GenUI 不是通用转换器，它已经**与内部组件库和 TCA 绑定**，意味着

- 生成的不是散装的 `Text` + `Rectangle`，而是**复用的内部组件**
- 生成的不是裸 SwiftUI，而是**符合团队 TCA 规范的 Feature 骨架**
- UI 层的一致性由工具链保证，不依赖每个开发者（或每次 AI 调用）的自觉

**换句话说：路线 A 所需的基础设施已经就绪，成本曲线上的"前期投入"实际比从零开始低得多。**

## 4. 成本模型

> 以下为**相对指数，不是预算**。单位是"相对人日单位"，需用团队实际数据校准后才能用于排期。

**假设条件**（请按实际情况调整）：
- 目标约 50 屏
- 迁移期内设计改稿 ≥ 4 次（这是保守估计，实际通常更多）
- 每次改稿平均影响 8 屏

| 项目 | 路线 A：Figma + GenUI | 路线 B：源码推导 |
|---|---|---|
| 前期投入（GenUI 就绪 / Figma 治理 / 标注规范 / 组件库补齐） | 45 | 5 |
| 首批 50 屏产出 | 66 | 110 |
| **上线前小计** | **111** | **115** |
| 每次设计改稿的边际成本 | **+9** | **+43** |
| 4 次改稿后累计 | **147** | **287** |
| 6 次改稿后累计 | **165** | **373** |

**三条解读**：

1. **上线前两条路线成本基本持平**（111 vs 115）。路线 A 前期多花的准备工作，被批量生成阶段的效率抵消掉了。
2. **真正的差距在上线之后**：每次改稿，A 的成本约为 B 的 **1/5**。
3. 成本只是可见的一半。**不可见的一半是质量**：路线 B 与设计的偏差会随时间累积，且没有任何机制阻止它累积。这份债会以"界面越改越乱、新人看不懂、改一处崩三处"的形式在半年后显现。

## 5. Flutter 源码去哪了：它承担另一半工作

这一点请务必在汇报中说清楚 —— **我们没有丢弃已有资产，只是把它放在了它擅长的位置。**

| 内容 | 藏在哪里 | 谁能拿到 |
|---|---|---|
| **UI 视觉** | Figma | GenUI ✅ |
| **业务规则、校验逻辑、状态流转** | **Flutter 源码** | 只有它能提供 |
| **API 语义、错误含义、边界处理** | **Flutter 源码** + 抓包 | 只有它能提供 |
| **交互流程、导航副作用** | **Flutter 源码** + 真机录屏 | 只有它能提供 |

Figma 描述"长什么样"，源码描述"怎么运转"。两者缺一不可，但不能互相替代。

**具体做法**：AI Agent 只读 Dart 源码，产出一份**与语言无关的屏幕行为契约**（Screen Spec），包含状态机、边界场景、并发处理、埋点等 —— 然后 Agent 拿着这份契约 + GenUI 生成的骨架，去填充 TCA Reducer 里的业务逻辑。

> **分工的本质**：把"机器擅长的高重复结构化工作"给 GenUI，把"需要理解意图的工作"给 AI + 人。这是 AI 辅助开发里投入产出比最高的切分方式。

## 6. 常见质疑应答

**Q：AI 这么强，让它读 Flutter 代码生成 SwiftUI 不是更快吗？**
A：AI 擅长的是**结构化变换**（给它明确的输入产出确定的输出），不擅长的是**从噪声中提取被埋没的意图**。Flutter 源码里的 UI 恰恰属于后者 —— 有效的设计意图埋在 hack、废弃分支和跨端妥协里。用 AI 做它有把握的那半边（从行为契约生成 Reducer 逻辑），成功率才高。

**Q：Flutter 那边还在迭代，两套会不会不一致？**
A：不一致是**必然**的，问题是谁该跟上谁。路线 A 的规则清晰：**Figma 是唯一权威**，Flutter 那边如果发现与 Figma 不符，那是 Flutter 的 bug。路线 B 的规则是"以源码为准"，等于宣布设计稿是错的 —— 这个裁定需要产品介入每一处偏差，成本极高。

**Q：如果 GenUI 生成的有问题呢？**
A：确实会有一部分 Figma 模式 GenUI 覆盖不到（复杂自绘、特定动画等）。处理方式是把这部分**集中盘点成清单**，作为已知的手工区域，而不是散落在整个项目里随机出现。**可控的 20% 手工区，优于不可控的全项目不确定性。** 这份覆盖率矩阵是立项后第一周就要做的事。

**Q：会不会推迟工期？**
A：前期多约 1–2 人月（主要是 Figma 治理与 GenUI 覆盖率盘点）。从第 2 次改稿开始回本。**如果这个项目预期生命周期超过一年（几乎肯定），路线 A 是明显优的。**

**Q：GenUI 明显依赖于 Figma 文件质量，我们的 Figma 规范吗？**
A：这正是需要前期投入的地方（组件化、Auto Layout、Variables 绑定、状态变体补充）。这笔投入的价值不限于本项目 —— 它同时会改善 Flutter 端的设计还原度，并且是公司设计系统资产的一部分。**这是能沉淀下来的资产，不是一次性消耗。**

**Q：已经在 App Store 的 Flutter 版本怎么办？用户会看到不一样？**
A：视觉差异是有意的（以最新设计为准），但**业务行为必须保持一致**。所以除了 UI 管线，我们还需要做数据迁移和埋点对齐 —— 这部分不受 GenUI 影响，无论选哪条路线都要做。

---

## 7. 需要管理层支持的三件事

1. **批准前期投入**：约 1–2 人月用于 Figma 治理、标注规范与 GenUI 覆盖率盘点。**这笔钱花在项目最前面，但决定了后面所有工作的效率。**
2. **确立 Figma 的权威地位**：明确"设计与实现不符时以 Figma 为准"，偏差由 Flutter 端修正，而不是由新 App 迁就旧实现。**这条规则需要产品与设计负责人共同背书。**
3. **给窗口期定规矩**：新 App 上线前，Flutter 版仍会持续迭代一段时间。**建议这段时间新功能一律不在 Flutter 端做**，只做必修项，避免同一需求实现两遍。这条需要 PMO 层面确认。

---

## 8. 如果只能记住一句话

> **GenUI 让 UI 变成可重复生成的产物，源码推导让 UI 变成一次性的人工制品。**
> 这个项目要做的不是"把 Flutter 翻译成 Swift"，而是"借重写的机会建立一个可再生的产线"。选哪条路，决定了重写的收益是一次性的，还是长期的。
