# Flutter App → SwiftUI 原生重写：方案评审与落地细化

> 输入条件：Flutter 源码 ✅ / Figma Design ✅ / GenUI（Figma→SwiftUI）✅
> 目标：Swift + SwiftUI 原生重写，AI Agent 辅助
> 你的初步设想：Agent 扫描每个 Screen 的业务逻辑 + GenUI 生成 SwiftUI + TCA Screen + API 转 DomainModel SDK

---

## 0. 一句话结论

**骨架是对的**（Spec-First + 视觉自动生成 + 显式状态管理 + 领域层 SDK），方向不用改。但它目前是**三条并行线各自为战**，缺一条把它们焊起来的产线。

有三个结构性缺口，不补会在第 4–8 周集中爆雷：

| # | 缺口 | 后果 |
|---|---|---|
| 1 | **GenUI 产物被当成资产，实际是负债** | 视觉 95% 像 → 团队误判"完成 80%"，实际 30%；且它与 TCA 结构性不兼容，必须重写 |
| 2 | **"业务逻辑"没有提取清单** | Agent 只会描述 happy path 渲染树，状态机/错误恢复/并发控制全部静默丢失 |
| 3 | **没有灰度与回滚通道** | 只能全量一刀切上线，一次发版赌全部 |

## 1. 你的方案逐条评审

| 环节 | 你的设想 | 评估 | 必须补的 |
|---|---|---|---|
| Agent 扫描业务逻辑 | Agent 读 Dart，输出每个 Screen 的逻辑 | ⚠️ **方向对，但会漏** | 需要固定的 **Screen Spec 模板**强制提取维度；单靠代码只能得到 happy path，必须叠加抓包 + Flutter 端真机录屏 |
| GenUI 生成 SwiftUI | Figma 一键出 SwiftUI 代码 | ⚠️ **最大风险点** | 产物分级 + 卫生门禁；且必须限定为"布局骨架"，不承担状态 |
| 生成 TCA Screen | TCA 承载状态与副作用 | ✅ **契合本项目** | 但不必全量 TCA；需明确 TCA 与 GenUI 产物的结合方式（两层拆分） |
| API → DomainModel SDK | 抽领域层 | ✅ **正确且应最先做** | 分层要细化；必须先出 Mock 实现；API 契约来源有优先级 |

## 2. 切入点选择：四种切法与推荐组合

| 切入点 | 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| **A. 按 Screen 垂直切片** | 一个屏幕从 SDK→Feature→View→测试打通 | 早暴露管线问题，可并行复制 | 前期基础设施未稳时返工 | ✅ **主切法** |
| **B. Token + 组件库** | 先建 Design Token 与 App 级组件 | 后期批量生产快、视觉一致 | 不产生可见进度 | ✅ **前置一次性做** |
| **C. Domain SDK** | 先把所有 API/领域模型做完 | 后续屏幕开发不被后端阻塞 | 容易做成"过度设计"的大爆炸交付 | ✅ **与 B 并行，按屏幕需要增量做** |
| **D. 路由壳** | 先做原生壳 + 路由分发 + 空屏占位 | 立刻可跑、可灰度、可回滚 | 单独看不出价值 | ✅ **最先做，是所有风险的对冲** |

**推荐顺序：D 打壳 → B/C 打底 → A 批量生产。**

D 是关键：原生壳里同时挂 SwiftUI 路由和 Flutter module（`FlutterViewController`），**按路由表由远端配置决定走新屏还是旧屏**。这样每一个屏幕都能独立灰度、独立回滚 —— 这是唯一能把"一次性豪赌"变成"逐屏推进"的架构。

## 3. GenUI 的真相：怎么用才不踩坑

### 3.1 它能给 / 不能给

**能给**：结构意图（哪几块、什么层级、谁包谁）、精确的设计变量（间距/字号/色值）、组件边界的线索。

**不能给**（这些全在你的 App 里，Figma 里没有）：

- 状态变体：loading / 空态 / 错误 / 骨架屏 / 部分失败 / 离线 / 无权限
- 动态内容：文本超长、多行、无图、异步图、数字极大值
- 系统适配：深色模式、动态字体（Dynamic Type）、安全区、键盘避让、横屏/iPad/分屏、VoiceOver、RTL
- 状态绑定：它产出的是字面量，不是 `state.xxx`
- 行为：点击、埋点、节流、鉴权、路由

### 3.2 产物三分级

| 级别 | 判定 | 处置 |
|---|---|---|
| 🟢 可直接用 | 纯装饰叶子节点，零逻辑零数据（图标块、分割线、静态图文） | 走卫生门禁后入库 |
| 🟡 需重写 | 有数据绑定或状态变体的容器（列表项、卡片、表单行） | 保留布局骨架，替换字面量为状态引用 |
| 🔴 禁止用 | 绝对定位 / 硬编码 frame / 魔法色值 / ZStack 叠层模拟布局 | 一律重写，不允许 merge |

### 3.3 GenUI 卫生门禁（CI 机器检查，不靠人眼）

```
1. 禁止 Color(red:green:blue:) 字面量与 #hex → 必须走 DesignToken
2. 禁止 .frame(width:/height:) 硬编码尺寸（允许 maxWidth / minHeight）
3. 禁止 .position(x:y:) / .offset 做布局 → 必须 Stack + Spacer
4. 每个可被点击元素必须有 accessibilityLabel
5. 所有文本必须走 LocalizedStringKey，禁止裸字符串字面量
6. 数字间距必须来自 Spacing token，禁止 37 / 23 这类魔数
7. body 内禁止出现计算逻辑（只允许引用 state 字段）
```

### 3.4 估算陷阱（最危险的一条）

GenUI 出来的屏幕**在 happy path 上看起来完成了 95%**，会让整个团队（包括 PM）误判进度。真实完成度约 30%：剩余的是状态机、边界、适配、行为 —— 恰恰是最耗时的部分。

**对策**：进度度量只认 "通过 Parity Checklist 的屏幕数"，不认 "生成了多少行代码"。

### 3.5 让 GenUI 产物真正可复用的关键：两层拆分

```
XxxFeature (TCA)              ← Agent 写，持有状态机与副作用
    │
    ├── XxxViewState          ← 纯数据结构，View 只认这个
    │
    └── XxxLayout (SwiftUI)   ← GenUI 产物净化后落在这里，纯渲染
            let state: XxxViewState
            let send: (XxxAction) -> Void
```

`XxxLayout` 是一个**纯函数式渲染层**：输入 ViewState，输出 View，不持有任何 `@State`。这样：

- GenUI 产物的布局结构 100% 复用，只需要把字面量替换成 `state.xxx`
- 这个替换是**机械变换**，Agent 做可靠，人做无聊 —— 正好交给 Agent
- 状态全部收敛到 TCA Feature，可测试
- 将来换设计稿，只换 Layout 层，Feature 不动

> **这一步是整个方案能否落地的技术关键。** 不做两层拆分，GenUI 产物和 TCA 就是两套互斥的代码风格，最终必然是人工重写。

### 3.6 Figma 侧治理比事后修补便宜 10 倍

GenUI 输出质量 ≈ Figma 文件质量。开工前先做四件事：

1. **组件化**：重复出现的元素必须是 Figma Component，不是复制的图层
2. **Auto Layout**：所有容器开 Auto Layout（决定生成的是 Stack 还是绝对定位）
3. **绑定 Variables**：颜色/字号/间距绑定到 Figma Variable，且与 Design Token 命名一致
4. **补状态变体稿**：让设计补 空态 / 错误 / 加载 / 超长文本 / 无图 五张变体 —— **没有这些，GenUI 只能生成 happy path**

## 4. AI Agent 扫描：从"读代码"到"产出规约"

### 4.1 必须有 Spec 这道墙

```
Analyzer Agent（只读 Dart，禁止写 Swift）
        ↓  产出 Screen Spec
   ── 规 约 墙 ──
        ↓  只读 Spec
Implementer Agent（禁止读 Dart）
```

**为什么**：让实现 Agent 直接读 Dart，会生成"Dart 味的 Swift"—— `_buildBody()` 命名、深层嵌套、setState 思维、把 `FutureBuilder` 的坏习惯带进 Swift。Spec 是与语言无关的行为契约，是唯一能切断这个污染的手段。

### 4.2 Screen Spec 模板（核心交付物）

每个屏幕一份，Agent 必须填满，空项写 `N/A` 并说明原因，**不允许留空**。完整模板见 `templates/screen_spec.md`，概要：

```
## 身份     路由名 / 深链 / 来源文件 / 对应 Figma Frame
## 状态机   全部状态枚举 + 每个状态的进入条件与可见内容
## 数据     依赖的 API、模型字段、缓存策略、刷新时机
## 交互     每个可点击元素的动作 + 前置校验 + 副作用
## 边界     分页 / 下拉刷新 / 空态 / 错误 / 超时 / 离线 / 权限拒绝
## 导航     进参、出参（带回值）、返回拦截、路由守卫
## 生命周期 进入刷新、前后台、退出清理、页面时长统计
## 并发     请求取消、防抖节流、竞态处理（后发先至）
## 埋点     事件名 + 参数（必须与 Flutter 侧 1:1）
## 平台     推送/深链/相机/相册/生物识别/Keychain
## 视觉     用到的 Design Token、Figma 差异点
## 风险     AB 分支、灰度、自绘、三方 SDK
```

**"状态机"和"并发"两节是 Agent 最容易漏的**，必须在 prompt 里点名要求，并给出反例说明。

### 4.3 单靠读代码不够 —— 四个输入源

| 源 | 提供什么 | 获取方式 |
|---|---|---|
| Dart 源码 | 结构、意图、命名 | 直接读 |
| **真机抓包** | **真实 API 契约、字段、错误码** | Charles / mitmproxy 跑一遍 Flutter App |
| **真机录屏** | **真实交互流程、转场动画、状态切换** | 每个屏幕录一段操作视频 |
| Figma | 视觉与 token | GenUI + 人工 |

> 抓包的优先级高于读 Dart 代码：代码里写的是"开发者以为的契约"，抓包才是"后端实际的契约"。分页参数、错误码、字段可选性经常不一致。

### 4.4 上下文切片（大仓库必做）

Dart 仓库全量投喂必然爆上下文。做法：

1. 从入口路由出发，构建文件依赖图
2. 每个 Screen 取 **N 跳内可达文件**（N=2 通常够）
3. 可达文件超过阈值时，公共层（theme / network / utils）用**摘要**而非全文
4. 用上一轮的 `tools/scan_flutter_widgets.py` 先出组件清单，作为 Agent 的"地图"

### 4.5 Agent 角色编排

| 角色 | 输入 | 输出 | 硬约束 |
|---|---|---|---|
| Analyzer | Dart + 抓包 + 录屏 + Figma | `Screen Spec`（Markdown） | 禁止写 Swift |
| SDK Builder | API 契约 | DomainModel SDK + Mock | 禁止引用任何 View |
| Layout Producer | Figma + Spec 的视觉节 | `XxxLayout.swift` | 禁止写状态逻辑 |
| Feature Builder | Spec + SDK | `XxxFeature.swift`（TCA） | 禁止读 Dart |
| Reviewer | 上述产物 + Spec | 编译结果 + Parity 报告 | 必须通过门禁才合并 |

## 5. TCA：该不该上

### 5.1 它在这里的真正价值（不只是"架构好看"）

TCA 的三个特性**正好对准本项目的三个难点**：

| TCA 特性 | 对准的问题 |
|---|---|
| `State` 必须穷举 | 强迫把 Flutter 里**隐含的状态机**显式化 → 直接补上 §4.2 的"状态机"节 |
| `Effect` 显式声明副作用 | 网络/定时器/埋点不再散落在 View 里 → 解决"行为层静默丢失" |
| `@Dependency` 依赖注入 | DomainModel SDK 以依赖形式注入 → `TestStore` 里直接换 Mock |

**结论：TCA 不是装饰，它是"行为对等"这个目标的工程载体。** 这是它值得上的核心理由。

### 5.2 但不要全量上

| 屏幕类型 | 建议 |
|---|---|
| 有状态机/副作用/多步流程（下单、支付、表单、播放器、IM） | ✅ TCA |
| 纯展示 + 单一网络请求（详情、关于、静态页） | ⚠️ `@Observable` + ViewModel 即可 |
| 纯静态（协议页、空壳页） | ❌ 直接 SwiftUI |

全量 TCA 会把简单页成本抬高 2–3 倍，且拖累编译速度。

### 5.3 三条落地约束

1. **Swift 6 language mode 前置**：新项目直接开严格并发 + `Sendable`，别等写完再返工。注意 TCA 与严格并发有已知摩擦（部分需 `@preconcurrency import`），先用一个屏验证
2. **依赖策略**：TCA 是三方库，需过公司合规审批；锁定版本，不要跟 main
3. **团队斜率**：TCA 学习曲线陡，建议先用 2 个试点屏跑通，配一份内部 Cheat Sheet，再铺开

## 6. DomainModel SDK：细化分层

```
┌─ NetworkKit    URLSession + async/await、拦截、重试、Token 刷新、日志
├─ DTO           Codable，与 API 一一对应（有 OpenAPI 就生成）
├─ Mapping       DTO ⇄ Domain，显式转换，不隐式
├─ Domain        纯 Swift 值类型、Sendable、无网络概念、含业务不变量
├─ Repository    protocol + 实现，唯一对外入口
├─ Persistence   缓存 / SwiftData / Keychain
├─ Error         AppError 分类枚举（不是裸 URLError）
└─ Mock          fixture 实现，与真实实现同 protocol
```

**六条硬规则**：

1. **DTO 与 Domain 必须分离** —— Flutter 侧 `json_serializable` 生成的类常被直接当领域模型用，Swift 侧别继承这个坏习惯
2. **先出 Mock 实现** —— 屏幕开发不阻塞于后端联调，且 `TestStore` 直接用
3. **API 契约来源优先级**：OpenAPI/Swagger（生成） > 真机抓包 > 读 Dart 代码
4. **重试/幂等/取消/竞态收口在 SDK 层**，不要散落到各屏幕
5. **错误分类枚举**：网络错误 / 业务错误（带 code）/ 鉴权失效 / 解析失败，View 层只认这个枚举
6. **按屏幕需要增量做**，不要一次性把所有 API 做完

**易漏的四个**（SDK 层统一处理，屏幕层完全不感知）：
- 请求取消（页面退出时 `task.cancel`）
- 竞态：后发先至导致旧响应覆盖新数据（Flutter 里 dio cancelToken 处理过，Swift 侧容易漏）
- Token 刷新并发合并（多个 401 同时触发刷新会打爆后端）
- 幂等键（下单/支付类接口）

## 7. 你还没提到的 9 个坑

### ① 老用户本地数据迁移（最容易漏、最伤用户）

Flutter 侧的本地数据，SwiftUI 版本读不到：

| 存储 | iOS 实际形态 | 迁移方式 |
|---|---|---|
| SharedPreferences | `UserDefaults`，key 前缀 `flutter.` | 原生可直接读，写一次性迁移 |
| Hive / Isar / sqlite | App Group 内文件 | 需读文件路径，解析后转写 |
| secure_storage | Keychain | 需指定同一 accessGroup |
| 图片缓存 | 沙盒文件 | 可弃 |

**不做 = 老用户升级后登录态丢失、草稿丢失。** 必须在 Phase 0 就列清单。

### ② 埋点口径对齐（最容易静默失败）

事件名/参数必须与 Flutter 侧 1:1，否则数据断流、历史报表断层。

**做法**：从 Dart 提取全量埋点清单 → 建映射表 → **CI 断言 SwiftUI 侧实现的事件集合 == Flutter 侧清单**。这是最晚被发现的问题（上线一两周后数据分析才发现），必须自动化。

### ③ Figma 与 Flutter 源码冲突时的裁决规则

Figma 常是"理想的/旧的"，Flutter 源码才是"真实实现的"。**冲突时以谁为准必须事先定死**：

> 默认：**行为以 Flutter 源码为准，视觉以 Figma 为准**；冲突处产出"差异清单"交产品裁决，不允许开发自行选择。

### ④ iOS HIG 重新定性

Flutter 一套代码两端跑，很多设计是"两端都凑合"。转原生后要按 iOS 规范重新定性：导航栏与返回手势、安全区与刘海、键盘避让、动态字体、VoiceOver、长按菜单、系统分享、Haptic。Figma 里通常没画这些。

### ⑤ 视觉回归对比闭环（否则"还原度"永远在吵架）

> Flutter golden test + SwiftUI snapshot test（swift-snapshot-testing），**用同一份 fixture 数据驱动两边**，逐屏输出对比图。

没有这个，"像不像"全靠人眼和争吵。有这个，还原度是一个可跑的数字。

### ⑥ 双端并行与灰度通道

见 §2 的 D。原生壳 + 路由分发 + 远端开关，是唯一能逐屏上线、独立回滚的架构。**没有它，你只能在"全量上线"和"无限延期"之间二选一。**

### ⑦ 性能基线重建

Flutter 转原生后包体下降，但列表滚动帧率、冷启动、内存需要**重建基线**。SwiftUI 列表常见坑：`LazyVStack` 配不稳定 `id` 导致整列表重绘、`body` 内做重计算、无 `@Observable` 导致过度刷新。

### ⑧ Parity Checklist（验收的唯一标准）

每个屏幕一份，逐项打勾才允许合并。内容由 Screen Spec 自动生成，包含：状态全覆盖、边界全覆盖、埋点全覆盖、视觉对比通过、Token 无硬编码、 accessibility 通过。

### ⑨ 自绘与三方 SDK 的提前定性

`CustomPainter` / `BackdropFilter` / Shader / Platform Channel / 广告推送地图 SDK / **Shorebird 类代码热更（iOS 不允许，必须砍掉并改需求流程）**。这些 Phase 0 就要扫出来，因为它们决定工期是 2 周还是 2 个月。

## 8. 落地路线图

| Phase | 内容 | 产出 | 关键门禁 |
|---|---|---|---|
| **P0 定性** (1–2w) | 组件清单扫描、自绘/三方/热更定性、本地数据清单、埋点清单、Figma 治理 | `CONVERSION_PLAN.md` + 风险登记表 | 工期可估算 |
| **P1 基础设施** (2w) | 原生壳 + 路由分发 + 灰度开关；Design Token 桥；App 级组件适配层 | 可运行的空壳 App，能加载 Flutter module | 壳能跑通新旧路由 |
| **P2 SDK** (2–3w，与 P1 并行) | DomainModel SDK 分层 + Mock 实现 | SDK + fixture | 单元测试覆盖 Mapping / Error |
| **P3 试点** (2w) | **3 个代表性屏幕**走完整管线 | 3 个 TCA Feature + Layout + 测试 | Pipeline 跑通，产出 Cheat Sheet |
| **P4 批量生产** | 按模块并行，每屏走 Spec→SDK→Feature→Layout→门禁 | 屏幕池 | Parity Checklist 全勾 |
| **P5 灰度** | 逐屏开开关，视觉回归 + 埋点断言 + 崩溃监控 | 灰度报告 | 崩溃率/ANR 不劣化 |
| **P6 下线** | 移除 Flutter module、清理桥接与迁移代码 | 纯原生 App | — |

**P3 试点屏的选择标准**（要能一次性暴露管线全部难点）：

1. 一个**简单列表屏**（验证基础管线：列表 + 分页 + 空态）
2. 一个**复杂表单屏**（验证状态机 + 校验 + 提交 + 错误恢复）
3. 一个**有自绘或复杂动画的屏**（验证最难映射路径）

不要挑最简单的三个屏做试点 —— 那样 P4 才会第一次遇到难题，代价放大十倍。

## 9. 风险登记表

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| GenUI 产物不可维护 | 高 | 高 | 两层拆分 + 卫生门禁 + 三分级 |
| Agent 漏提状态机/边界 | 高 | 高 | Screen Spec 强制模板 + 抓包 + 录屏 |
| 埋点断流 | 中 | 高 | 埋点清单 + CI 断言 |
| 老用户数据丢失 | 中 | 高 | P0 列清单 + 一次性迁移桥 + 灰度验证 |
| Figma 与实现不符 | 高 | 中 | 差异清单 + 产品裁决流程 |
| TCA 团队上手慢 | 中 | 中 | 试点 + Cheat Sheet + 不全量使用 |
| 无限期双端维护 | 中 | 高 | P6 必须有硬性时间点 |
| iOS 不允许代码热更 | 确定 | 中 | 需求流程改造，P0 就沟通 |

## 10. 立刻可以做的五件事

1. 跑 `python3 tools/scan_flutter_widgets.py --path <你的Flutter仓库> --out ./out` 出组件清单与风险打标
2. 抓包跑一遍 Flutter App，导出 API 清单（这是 SDK 的事实源）
3. 给每个屏幕录一段操作视频 + 截图（Agent 的输入，也是视觉回归基线）
4. 找设计要五张状态变体稿（空态/错误/加载/超长文本/无图）
5. 挑出 P3 的三个试点屏，先跑通一条完整管线再铺开
