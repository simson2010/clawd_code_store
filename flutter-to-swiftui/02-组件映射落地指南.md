# Flutter UI 组件 → SwiftUI / 公司自定义组件：落地指南

> 承接《Flutter 源码 → SwiftUI iOS App 迁移路径调研报告》。本文只谈 UI 组件层怎么落。

---

## 0. 两个必须先在脑子里转过来的认知

### 认知一：不是「widget 找 View」，是「widget 找一组 Modifier」

Flutter 里**一切皆 Widget** —— 布局、样式、装饰都是节点；SwiftUI 里一个 View 挂一串 Modifier，**每个 modifier 都是一次包装**。

```dart
// Flutter：一个 Container 承担了四件事
Container(
  padding: EdgeInsets.all(16),
  decoration: BoxDecoration(
    color: surface,
    borderRadius: BorderRadius.circular(12),
    boxShadow: [BoxShadow(blurRadius: 8, color: shadow)],
  ),
  child: content,
)
```

```swift
// SwiftUI：拆成四个 modifier
content
  .padding(16)
  .background(surface, in: .rect(cornerRadius: 12))
  .shadow(radius: 8)
```

**所以映射的最小单位不是 View，是 Modifier。** 按"一个 widget 换一个 View"去查表，产出的必然是嵌套噪音。

### 认知二：视觉权威变了

Flutter 端 App 自己说了算（Material / Cupertino / 全自绘都行）。
SwiftUI 端有**两个**权威：Apple HIG + 公司 Design System。

> **这一步最容易被跳过，代价也最大**：如果源 App 是 Material 风格，迁移不是"换语言"，是"重新定性视觉"。必须先跟设计确认：iOS 端到底跟着原生 HIG 走，还是像素级复刻 Flutter？这决定了后面所有工作量。

## 1. 三层拆解模型（贯穿全文的方法）

拿到任何一个 Flutter 组件，不要整体映射，先拆三层：

| 层 | 内容 | 该怎么处理 |
|---|---|---|
| 🎨 **视觉层** | 颜色 / 字号 / 间距 / 圆角 / 阴影 / 图标 / 动效时长 | → 走 **Design Token**，不进组件映射表 |
| 🧱 **结构层** | 布局关系、滚动行为、层叠、safe area | → SwiftUI 容器 + modifier 组合 |
| ⚙️ **行为层** | loading / disabled / 点击节流 / 焦点 / 滚动控制 / 埋点 / AB 开关 | → **显式代码**，没有等价映射 |

### ⚠️ 血泪坑：公司自定义组件把三层焊死了

公司自研的 `AppButton` 通常不只是"一个蓝按钮"，里面往往藏着：

- loading 态自动禁用点击
- 点击节流（防连点）
- 埋点上报（点一次报一次）
- AB 实验分支
- 权限/登录态拦截

**只做视觉映射 = 行为层静默丢失。** 上线后最典型的三个故障：埋点数据断流、连点导致重复下单、未登录点击崩溃。

> 判据：组件里有 `Timer` / `ScrollController` / `TextEditingController` / `analytics` / `track(` 之类符号的，**必须**逐行读实现，不能靠签名猜。

## 2. 决策矩阵：拿组件对着问，落到三条路径

```
Q1 是自绘 / 渲染型吗？  —— CustomPainter、RenderBox、BackdropFilter、ShaderMask、FFI
   └─ 是 → 路径 C：新建原生组件
Q2 公司 iOS DS 里有语义等价物吗？
   └─ 有 → 路径 B：适配层包装
Q3 承载业务语义吗？（埋点 / 节流 / 鉴权拦截 / AB）
   └─ 有 → 路径 C：新建组件 + 给 DS 提需求
   └─ 无 → 路径 A：原生 SwiftUI 组件 + modifier 直接用
```

| 路径 | 适用场景 | 产出 | 典型比例 |
|---|---|---|---|
| **A** 原生直用 | 纯容器、纯展示 | 直接 SwiftUI 组件 | 50~60% |
| **B** 适配层转发 | 公司 DS 已有对应物 | 薄 wrapper | 20~30% |
| **C** 原生新建 | 自绘 / DS 缺失 / 有业务语义 | 新组件（可能 UIViewRepresentable） | 10~20% |

## 3. 路径 A：映射到通用 SwiftUI 组件

### 3.1 结构层

| Flutter | SwiftUI | 备注 |
|---|---|---|
| `Column` / `Row` / `Stack` | `VStack` / `HStack` / `ZStack` | `spacing` 参数直接对应 |
| `Expanded` / `Flexible` | `Spacer()` / `.frame(maxWidth:)` | SwiftUI 没有 flex 系数，用 `LayoutPriority` 或 iOS 16+ `ViewThatFits` |
| `ListView.builder` | `List` / `LazyVStack` + `ScrollView` | 懒加载用 `LazyVStack`，不要 `VStack` |
| `GridView` | `LazyVGrid` + `GridItem` | `GridItem(.flexible())` ≈ `SliverGridDelegateWithMaxCrossAxisExtent` |
| `SingleChildScrollView` | `ScrollView(.vertical)` | — |
| `NestedScrollView` | ❌ 无等价 | 需自己用 `ScrollView` + sticky header 协调 |
| `SafeArea` | `.ignoresSafeArea()` 反向 / `safeAreaPadding` | 语义相反，注意方向 |
| `Scaffold` + `AppBar` | `NavigationStack` + `.navigationTitle()` | AppBar 的 `leading/trailing/actions` → `toolbar` |
| `BottomNavigationBar` | `TabView` | Flutter 的手势返回 vs iOS 侧滑返回，行为不同 |
| `Drawer` | 自定义 side panel | iOS 无原生抽屉，通常改成本页 push |
| `showModalBottomSheet` | `.sheet()` + `.presentationDetents()` | iOS 16+ 才支持自定义高度档位 |
| `showDialog` | `.alert()` / `.fullScreenCover()` | — |
| `SnackBar` | 无原生 | 自己写 overlay，注意别挡 TabBar |
| `Hero` | `.matchedGeometryEffect()` 或 `navigationTransition` | iOS 18+ 后者更省事 |

### 3.2 行为层陷阱（最容易踩）

| Flutter 行为 | SwiftUI 做法 | 坑 |
|---|---|---|
| `GestureDetector` 多手势共存 | `.simultaneousGesture()` / `.highPriorityGesture()` | 默认 chained gesture 优先级不同 |
| `TextEditingController` | `@State var text: String` | 不要在 ViewModel 里存 TextField 的值，会卡 |
| `FocusNode` | `@FocusState` | 键盘收起时机不同 |
| `ScrollController.animateTo` | `ScrollViewReader` + `scrollTo` | 需要给 item 加 `.id()` |
| `PageController` | `TabView(selection:)` 绑定 | Flutter 的 viewportFraction 需要额外做 |
| `RefreshIndicator` | `.refreshable {}` | 只有 iOS 15+，且必须是 ScrollView 的子树 |
| `WillPopScope` | iOS 侧滑返回 | iOS 不能直接拦截，得用 `navigationBarBackButtonHidden` + 自定义 |

## 4. 路径 B：映射到公司自定义组件 —— **适配层模式**

### ❌ 不要这样（业务页面直接裸调 DS）

```swift
// 业务代码里散落 DS 调用，将来换 DS / 灰度要全量改
DSButton(title: "立即支付", style: .primary) { pay() }
DSCard(shadow: .medium) { content }
DSTextField(placeholder: "手机号", validator: .phone)
```

### ✅ 要这样（App 自己有一层组件契约）

```swift
// AppUI/AppButton.swift —— 全 App 唯一依赖 DS 的地方
public enum AppButtonVariant { case primary, secondary, danger }

public struct AppButton: View {
    let title: String
    var variant: AppButtonVariant = .primary
    var isLoading: Bool = false
    var fullWidth: Bool = true
    let action: () -> Void

    public init(_ title: String,
                variant: AppButtonVariant = .primary,
                isLoading: Bool = false,
                fullWidth: Bool = true,
                action: @escaping () -> Void) {
        self.title = title
        self.variant = variant
        self.isLoading = isLoading
        self.fullWidth = fullWidth
        self.action = action
    }

    public var body: some View {
        // 只在这一处对接 DS，其余 300 处业务代码不知道 DS 的存在
        DSButton(title: title, style: mapVariant(variant), isBusy: isLoading) {
            Analytics.track("button_tap", ["title": title])  // 行为层在这里补齐
            action()
        }
        .frame(maxWidth: fullWidth ? .infinity : nil)
    }

    private func mapVariant(_ v: AppButtonVariant) -> DSButtonStyle {
        switch v {
        case .primary: return .primary
        case .secondary: return .secondary
        case .danger: return .destructive
        }
    }
}
```

### 为什么这层不能省

| 收益 | 说明 |
|---|---|
| **灰度共存** | Flutter 与 SwiftUI 长期并行时，适配层里可以切「走 DS / 走系统组件 / 走新实现」三档开关 |
| **补 DS 缺口** | DS 没有的 `fullWidth` / `danger`，在适配层兜，不用改 DS |
| **行为层收口** | 埋点、节流、鉴权拦截只写一次 |
| **换 DS 不求人** | 换供应商改一个文件 |

### 适配层的落地顺序

1. 先**只建空壳**（struct + init + 转发到系统组件），让全项目编译通过
2. 再逐个把转发目标换成 DS 组件，一个 PR 一个组件
3. 每个组件配套一个 `#Preview`，四态对照（默认 / loading / disabled / 错误）

## 5. 路径 C：必须新建的原生组件

| Flutter 来源 | SwiftUI 方案 | 备注 |
|---|---|---|
| `CustomPainter` | `Canvas { ctx, size in ... }` | 手绘路径可直接搬，性能更好 |
| `CustomClipper` | `Shape` 协议 + `Path` | 写成 `struct XXXShape: Shape` 复用性最高 |
| `BackdropFilter` | `.background(.ultraThinMaterial)` | iOS 26 Liquid Glass 用 `.glassEffect()` |
| `ShaderMask` / 大面积 GLSL | Metal Shader + `UIViewRepresentable` | 有 SwiftUI 的 `Shader` API 但能力弱于 GLSL |
| `RenderBox` 自定义布局 | `Layout` 协议（iOS 16+） | iOS 16 以下要 `UIViewRepresentable` 兜底 |
| 三方地图 / 相机 / WebView | 官方 iOS SDK + `UIViewRepresentable` | 一律桥接，不重写 |

**自绘组件的一条硬建议**：先问一句"这个自绘在 iOS 上是不是本来就该是个原生控件"。大量 Flutter 里的"自绘组件"（环形进度、手写签名、波浪动画）在 SwiftUI 里是几十行 `Canvas`，比 Flutter 版本还短 —— 别紧张。

## 6. Token 桥：让公司自定义组件真正可落地

**组件对齐的前提是 token 对齐。** 组件没对齐会难看，token 没对齐会**永远对不齐**。

### 做法：一份源，四个平台生成

```
tokens/source.tokens.json        ← W3C Design Tokens 格式，唯一真源
        │  Style Dictionary v5
        ├─→ ios/DSColors.swift   → Color.apDynamic(light: Color(apHex:0x155DFC), dark: ...)
        ├─→ ios/DSSpacing.swift  → enum AppSpacing { static let space4: CGFloat = 16 }
        ├─→ ios/DSTypography.swift（带 Dynamic Type 锚点）
        ├─→ compose/...
        └─→ flutter/DSTheme.dart → ThemeData.light() / ThemeData.dark()
```

- 开源工具：**Style Dictionary**（Amazon）+ W3C Design Tokens 规范；现成的商业管线 Appetite UI 也是同一套路。
- Figma variables 与代码 token 共用同一套 ID。

### 三条硬规则

1. **永远不要** `DSColors.blueLight` / `DSColors.blueDark` 这种值级命名。
   要语义化：`Color.surfacePrimary` / `Color.textSecondary`。视图代码在明暗模式下必须**完全一致**，由 accessor 根据 `colorScheme` 解析。
2. **契约测试**：CI 里断言每个语义 token 在每个平台的生成产物里都存在（名字一致，值可以不同）。这能挡住"加了新 token 但只重新生成了 Web"。
3. **禁止手改生成文件**：CI 里 regenerate + git diff，脏了就 fail。这条专门防"紧急热修"。

### 迁移期的讨巧顺序

不要一上来做组件，顺序倒过来：

```
Week 1  token 落地（颜色/字号/间距/圆角/动效）→ 先让 Flutter 端也接同一批 token
Week 2  高频组件适配层空壳（Button / Card / TextField / List row）
Week 3  逐屏重写 + 视觉回归
Week 4  token lint 进 CI，禁止新增硬编码色值
```

好处：Week 1 结束就可以在 Flutter 端验证 token 是否覆盖全，避免在 SwiftUI 端做了一半才发现缺十个语义色。

## 7. 用脚本把第一步跑起来

```bash
python3 tools/scan_flutter_widgets.py --path D:/projects/your_app --out ./mapping-out
```

产出三张表：

| 文件 | 内容 | 用途 |
|---|---|---|
| `widget_inventory.csv` | 全部自定义组件：基类、引用次数、参数清单、风险信号、路径 | 排期依据 |
| `widget_inventory.md` | 疑似 DS 组件 / 全量清单 / SDK 用量 | 评审用 |
| `widget_inventory.json` | 结构化数据 | 喂给 Agent 继续分析 |

脚本会额外告诉你三件事：

1. **UI 基线** —— Material 还是 Cupertino 还是纯自绘（决定是否要重新定性视觉）
2. **疑似 DS 组件** —— 引用广 + 命名成体系 + 放在 `widgets/` 目录下的，优先处理
3. **行为层信号** —— 组件里有埋点 / Timer / Controller / 模糊 / 自绘的，打标警告

## 8. 验收清单（每个组件打勾才能过）

| 项 | 为什么重要 |
|---|---|
| 四态对齐：默认 / 加载 / 空 / 错误 | Flutter 端 `AsyncValue` 三态，SwiftUI 端容易只写加载+成功 |
| 暗黑模式 | Material 的 elevation 在暗色下和 iOS 语义色不同 |
| Dynamic Type 超大字号 | 固定高度布局会炸 |
| VoiceOver 焦点顺序与标签 | Flutter 的 Semantics 标签不会自动转过来 |
| **埋点事件名与原 Flutter 完全一致** | 最常被漏，且上线后不可逆（数据断层） |
| iPad / 横屏 | Flutter 通常不做，iOS 用户会做 |
| 截图对比（同一设备、同一数据） | 唯一的客观验收手段 |

## 9. 一句话总结

> **叶子组件映射到 token，容器组件映射到 modifier，只有公司自定义组件才需要"组件级"思考，而它们 90% 的工作量在行为层不在视觉层。**
