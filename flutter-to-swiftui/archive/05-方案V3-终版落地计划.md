## 1. 四个新事实的重估

### 1.1 GenUI 是内部自研且已绑定组件库 + TCA —— 这是决定性的

这是本次补充中最有价值的一条。它一次性消灭了 V2 的头号风险（§5.1 组件映射 POC 通不过），并且让产线可以重构成**边界极其清晰**的形态：

| | 谁负责 | 产出性质 |
|---|---|---|
| **UI 与 TCA 骨架** | GenUI（Figma → 代码） | **可再生的**：设计改稿就重新生成 |
| **业务逻辑（Reducer 内部）** | AI Agent（读 Dart Spec） | **持久的**：手写一次，长期维护 |

这个分工之所以理想，是因为它恰好按"机器擅长 / 需要理解"切分：

- **结构化、确定性、高重复** → 机器（Figma → SwiftUI + TCA 样板）
- **需要理解意图、需要推断隐含规则** → Agent + 人（Dart 源码里的业务规则）

> **结论**：V2 里建议的"GenUI 组件映射 POC"不再是最大风险，**降级**为常规验证（仍需做，但不必前置到第一天）。

### 1.2 Flutter 会先推向 C 端 —— 三个风险复活 + 一个窗口期出现

② 让项目回到"存量 App 迁移"的性质。复活的三个风险：

1. **本地数据迁移**（最重要的用户可感知风险）
2. **埋点口径对齐**（最容易静默失败、最晚被发现）
3. **关键路径视觉回归**（用户对改版敏感）

新出现的问题是：**窗口期**（Flutter 上线 → Native 上线）。这期间 Flutter 仍在迭代，产生三个连锁问题 —— 见 §4。

### 1.3 Bundle ID 相同，覆盖安装 —— 接受，附三条运营注意

你说不是问题，我同意。但有三条执行层面的事建议现在就排好，避免临场手忙脚乱：

1. **版本号要提前排**：Native 版本号必须 > Flutter 最后版本；万一要回滚，回滚版还要 > Native 版。Build 号单调递增。这条现在排好，比届时应急处置省三天。
2. **覆盖安装保留沙盒** —— 这既是数据迁移的前提（好事），也意味着**脏数据会跟着过来**（坏事）。迁移逻辑要有容错。
3. **App Store 提审回滚不是即时的** —— 即使有 expedited review 也是小时级。**所以 §2 的 Kill switch 价值不降反升**：发现严重问题时，先用服务端开关止血，而不是指望回滚版本。

### 1.4 复用自建网络库 —— SDK 职责收窄，但要补四个能力

DomainModel SDK 不再需要自己的传输层，改为：

```
自建网络库（传输、拦截、鉴权、Token 刷新）
        ↓
  Repository 实现层        ← 复用网络库发请求
        ↓
  DTO ⇄ Domain Mapping     ← SDK 核心，这是真正要新建的部分
        ↓
  Domain Model（Sendable 值类型、含业务不变量）
        ↓
  AppError 分类（不是裸网络错误）
        ↓
  Mock 实现（同 protocol）
```

**必须盘点的四项网络库能力**，缺哪块就在 SDK 里补哪块：

| 能力 | 缺失后果 | 补齐位置 |
|---|---|---|
| async/await 接口 | Repository 要写 callback→async wrapper（大量样板） | SDK Wrapper 层 |
| **请求取消** | 页面退出后响应回来改写已销毁 State → 难查的崩溃 | SDK Wrapper |
| **Token 刷新并发合并** | 多个 401 同时触发刷新，打爆后端 + 状态错乱 | 网络库 or SDK |
| mock / stub 能力 | TestStore 无法脱离真实网络跑 | SDK Mock 层 |

**另一条容易忽略的**：网络库是否 Swift 6 / Sendable ready？老库往往不是，会直接影响能否开 Swift 6 language mode。若不是，要么包一层 Sendable Wrapper，要么退回 Swift 5 mode —— **这个决定要早做，因为它影响全项目代码风格**。

## 2. 重构后的产线与文件所有权（关键工程决策）

### 2.1 可再生层 vs 持久层

**这是 V3 最关键的工程决策。** GenUI 会反复重新生成。如果它的输出和手写的 Reducer 逻辑混在同一个文件里，**第二次设计改稿就会灾难性地吃掉业务逻辑**。

必须做**物理隔离 + CI 守护**：

| 文件 | 生成方 | GenUI 可否覆盖 | 内容 |
|---|---|---|---|
| `XxxView.swift` | GenUI | ✅ 随时覆盖 | 纯渲染，只读 ViewState |
| `XxxViewState.swift` | GenUI | ✅ | UI 展示字段（GenUI 从 Figma 推导） |
| `XxxViewAction.swift` | GenUI | ✅ | 点击 / 输入等来自 UI 的 Action |
| `XxxDomainState.swift` | Agent / 人 | ❌ | 真实业务状态机（来自 Dart Spec） |
| `XxxDomainAction.swift` | Agent / 人 | ❌ | API 结果、业务事件 |
| `XxxLogic.swift` | Agent / 人 | ❌ | Reducer 主体、Effect、依赖调用 |
| `XxxFeature.swift` | Agent / 人 | ❌ | 组合 reducer，永不被覆盖 |

**CI 规则**：GenUI 输出目录中若出现 ❌ 类文件，直接报错。这条要有测试守护，不能只靠口头约定。

**一个漂亮的副作用**：当 GenUI 重新生成导致 ViewAction / ViewState 签名变化，❌ 层会**编译失败** —— 这恰恰是我们要的变更信号。**编译器就是免费的变更检测器**，不需要额外工具。团队只需约定：**编译错误 = 设计发生了结构性变更，按错误信息去修逻辑层**，而不是随便改名让它编译过。

### 2.2 三层 State 分离（解决 GenUI State 与真实状态机的冲突）

GenUI 生成的状态通常是朴素的（`isLoading` + 数据），而 Dart Spec 提取出的真实状态机要丰富得多（空/错/离线/无权限/部分失败/加载更多…）。两者会打架。

解法是分层而不是merge：

```swift
struct XxxState {
    var view: XxxViewState        // GenUI 生成，可再生
    var domain: XxxDomainState    // 手写，持久 —— 真实状态机在这里
}
```

View 只读 `state.view`；Reducer 主要驱动 `state.domain`，再同步投影到 `state.view`。**GenUI 永远不知道 `domain` 层的存在**，也就不可能破坏它。

## 4. Flutter 双线期的变更同步机制（G7）

窗口期内 Flutter 仍在迭代，会产生三个问题：

1. **Spec 过期** —— 提取完的 Screen Spec 描述的是旧版本
2. **需求重复实现** —— 新需求两边都要写
3. **Native 上线时功能落后** —— 用户在 Flutter 版有的功能，新版没有

**机制建议**：

| 措施 | 做法 |
|---|---|
| **冻结基线** | 选一个 Flutter 版本号作为 Spec 基线，写进 `SPEC_BASELINE.md` |
| **发版 diff 同步** | Flutter 每次发版 → diff → 更新受影响屏幕的 Spec，标记为 `SPEC_CHANGED` |
| **需求分流策略** | 窗口期内，Flutter 端只做「必修」：崩溃修复、合规、服务端配合项。**新功能一律不做** —— 这是控制双份成本的唯一办法 |
| **窗口期上限** | 设一个硬性时间点（建议 ≤ 6 个月），过期仍未上线则重新评估 |

> **这条要写进项目章程**：窗口期的新功能需求怎么处理，必须在开始前就有规则，否则一定会临时扯皮。

## 5. 服务端双客户端兼容期（G8）

Native 上线 ≠ 所有用户立刻到新版。会有相当比例用户停留在 Flutter 版（不更新、系统版本不够、手动关了自动更新）。

必须在**Flutter 上线第一天**就规划：

| 项 | 说明 |
|---|---|
| **API 版本策略** | 请求带 clientType + version header，服务端据此分流。**现在就加**，不要等 Native 上线那天 |
| **响应向后兼容** | 服务端新增字段、改枚举，必须保证旧客户端不崩（旧客户端往往对未知枚举值不做兜底） |
| **停止支持时间点** | 明确"最低支持客户端版本"，到期在旧版里强制弹更新 |
| **灰度维度** | 不要按 App 版本灰度业务 —— 两个客户端的数据不能混着看 |

## 6. 数据迁移详细方案（复活的头号用户风险）

### 6.1 核心建议：在 Flutter 端「预埋导出」

**不要**让 Native 端去猜 Flutter 插件的私有存储格式（Hive 的二进制、sqflite 的库表结构）。这在工期和风险上都不划算。

**做法**：在 Flutter 端的**倒数第二个版本**里，加一段一次性导出代码 —— 把关键数据序列化成一个 JSON 写到共享位置（App Group 容器，`path_provider` 可访问）。Native 首启动时读取、转换、写库，然后删除。

**为什么这样最好**：
- Flutter 侧读自己的数据是最可靠的，不用担心格式猜错
- Native 侧只处理一个稳定的 JSON 契约，与 Flutter 内部实现解耦
- 契约可版本化（`version: 1`），未来再迁移也有迹可循

**时机要求**：这决定了"最后一个 Flutter 版本"必须提前规划。用户从更早版本升级上来的怎么办？—— **导出代码要在 Native 上线前至少两个版本就带上**，让绝大多数用户在覆盖面足够广之后才升级到 Native 版。

### 6.2 迁移内容清单

| 数据 | Flutter 实现 | iOS 落点 | 迁移难度 |
|---|---|---|---|
| 登录态 | shared_preferences / secure_storage | UserDefaults（key 前缀 `flutter.`）/ Keychain | 低—中 |
| 用户设置 | shared_preferences | UserDefaults `flutter.` 前缀，原生可直接读 | 低 |
| 草稿 / 离线数据 | sqlite / Hive | 私有文件 | **高** → 走导出 |
| 凭证 / Token | flutter_secure_storage | Keychain，需同 accessGroup 且 service/account 一致 | 中 |
| 图片 / 文件缓存 | path_provider | 可弃 | — |
| 浏览历史 / 足迹 | 通常 sqlite | 走导出 | 中 |
| **未完成的业务状态** | 购物车草稿、未提交表单、未完成下载 | 走导出 | **高，易漏** |

> 「未完成的业务状态」是业务部门最容易忽略、用户投诉最直接的一类。要专门找产品列出清单。

### 6.3 迁移执行规则（六条）

1. **同步执行、首启完成** —— 用户第一次打开就应该看到自己的数据，不接受"后台慢慢迁"
2. **有超时上限**（建议 2s），超时走降级路径，绝不能卡住启动
3. **幂等** —— 用标记位，用户多次启动不能重复迁移
4. **原子性** —— 失败则整体回滚到"未迁移"状态，允许下次重试；不允许半迁移
5. **保留源数据一个版本** —— 万一需要回滚到 Flutter 版，数据还在
6. **迁移结果必须上报埋点** —— 成功率、失败原因分布。**不上报 = 上线后你根本不知道有多少人数据丢了**

### 6.4 迁移的验证方式（不可省）

TestFlight 里做完整的升级路径验证：

```
安装最后一个 Flutter 版 → 制造数据（登录、设置、草稿、历史）
    → 覆盖安装 Native 版 → 逐项核对
```

这条必须进测试用例。**这是唯一能在上线前发现迁移问题的办法**，靠代码 review 看不出来。

## 7. 埋点对齐（复活的高风险项）

Flutter 上线后有历史数据，因此：

1. 从 Dart 提取全量埋点事件清单（V1 已有脚本思路）
2. 建 Flutter ↔ Tagging 映射表，三方对齐（Flutter 实际 / Tagging 文档 / Native 实现）
3. **CI 断言**：Native 实现的事件集合 == 映射表要求集合
4. 上线后**双端并行观测期**：新旧版本埋点数据分别建看板，确认口径一致后再合并
5. **特别注意自动埋点的去重窗口** —— Action 驱动的上报如果去重策略和 Flutter 版不一致，量级会差几倍，数据分析会误判

## 8. 修订路线图 P0–P7

| Phase | 内容 | 关键门禁 |
|---|---|---|
| **P0 定性**（2w） | ① **确认 SwiftUI 版组件库完备度（G6）** ② **GenUI Figma 覆盖矩阵（G1）** ③ **定再生/手写隔离 + CI 守护（G2）** ④ 三层 State 方案验证（G3） ⑤ Figma 标注规范（G4） ⑥ 网络库四项盘点（G9） ⑦ 迁移数据清单（§6.2） ⑧ 双线期窗口规则（§4） ⑨ Dart 埋点清单提取 ⑩ iOS target 签字 | G6 与 G1 有结论；迁移清单经产品确认 |
| **P1 管线搭建**（3w） | DesignKit 补齐、GenUI 适配内部组件库、隔离机制落地、**2 屏跑通端到端验证 §2 方案成立** | **改稿重生成一次，验证业务逻辑不丢** |
| **P2 Domain SDK**（2–3w，并行） | 基于自建网络库建 Mapping / Domain / Repository / Mock | 单测覆盖 Mapping 与 Error |
| **P3 迁移管道**（2w，并行） | Flutter 端导出代码 + Native 迁移器 + 迁移埋点 | TF 升级路径验证通过 |
| **P4 批量生产** | 按 Screen 生产，Parity Checklist | 逐屏通过 |
| **P5 双端并行验证** | Flutter 版 vs Native 版：关键路径视觉回归 + 埋点并行观测 + 迁移成功率 | 埋点口径一致、崩溃率不劣化 |
| **P6 上线** | TestFlight 分批 → Phased Release → Kill switch 待命 | 监控指标达标 |
| **P7 收尾** | Flutter 停更、最低版本提升、Flutter 仓库只读归档 | — |

> **P1 的出口标准请特别留意**：不是"生成了两个屏"，而是 **"改一次设计稿重新生成，业务逻辑不丢"**。这条验证不通过就进批量生产，代价会在 P4 集中爆发。

## 10. 需要立刻决策清单

## 11. 一句话总结

GenUI + 内部组件库 + TCA 让这件事从"高风险重写"变成"**有明确分工的工程流水线**"：**GenUI 管可再生的部分，Agent 管需要理解的部分，两者用文件所有权隔离**。而 Flutter 会上线这件事，把原本可以省掉的迁移与对齐工作全部请了回来 —— 这是目前最大的剩余风险源，且它的准备工作（导出代码、API versioning）**有提前量要求，必须现在排期，不能等到 Native 快上线时才做**。
