# 方案 V2：基于六条补充的修订与缺口分析

> 本文是 `Flutter转SwiftUI原生重写_方案评审与落地细化.md` 的修订版，不替代它。
> V1 中仍然有效的部分：两层拆分（Feature / ViewState / Layout）、Screen Spec 模板、Domain SDK 分层、 Agents 角色编排。
> V1 中被推翻的部分：灰度切换架构、本地数据迁移、视觉回归基准。—— 下面逐条说明。

---

## 0. 一个定性改变：这不是"迁移"，是"重写"

把 ①（Flutter 全丢、不要并行）和 ④（Flutter 还没推向 C 端）放在一起看，**项目性质变了**：

| | V1 假设 | V2 实际情况 |
|---|---|---|
| 性质 | 存量 App 迁移 | **未上线产品的技术栈重写** |
| 约束 | 行为必须与旧版逐帧对等 | 没有存量用户，**可以有取舍地重做** |
| 最大风险 | 用户感知到的行为回归 | **上线时间压力** |
| Flutter 资产的价值 | 必须复刻的行为基准 | **一份经过产品确认的需求规格说明书** |

这个转变带来两个重要结论：

**好消息**：我 V1 里排在前列的一堆风险可以整块删除 —— 本地数据迁移、埋点口径对齐、视觉回归 double-run、灰度AB双跑、双端长期维护。压力大幅下降。

**坏消息**：**不要再拿"行为对等"当 KPI**。没有用户，就没有对等的必要。真正该做的是**用 Flutter 源码做功能覆盖检查（coverage），而不是逐项对等检查（parity）** —— 也就是回答"Flutter 版有的能力，新版是不是有意保留了 / 有意砍掉了 / 还是漏掉了"，三种情况都要有明确记录。

> **行动建议**：把 V1 的 "Parity Checklist" 改名为 **"Coverage Checklist"**，每项三态：`已实现 / 有意砍（需产品签字） / 待确认`。只允许前两态通过。同时保留 Flutter 真机包作为 QA 与产品验收的参照物，**不要在 P0 就删 Flutter 仓库**，归档为只读。

## 2. 补充 3 直接回答：远端开关（Remote Toggle）是什么

你理解得对，就是**功能开关**。但它有两种形态，别混为一谈：

| 形态 | 说明 | 例子 |
|---|---|---|
| **a. 平台侧** | 独立的配置下发服务 + SDK，按 用户/设备/版本/灰度组 下发 JSON | Firebase Remote Config、LaunchDarkly、GrowthBook、公司自建配置中心 |
| **b. 代码侧** | App 内部一层 `FeatureFlag` 抽象，`if flags.foo` 且**必须**有默认值兜底（首启动无网络时不能崩） | `enum FeatureFlag: String { case checkoutV2 }` |

**关键修正**：V1 里我建议它，是为了解决"新 SwiftUI 屏 ↔ 旧 Flutter 屏 的切换"。**① 之后这个用途消失了** —— 没有旧屏可切。

那它还有没有价值？有，但换了个身份：

| 新用途 | 必要性 | 说明 |
|---|---|---|
| **Kill switch（紧急降级）** | ⭐⭐⭐ 高 | 某新屏出严重崩溃时，服务端下发配置隐藏入口 / 切 H5，不必等 App 审核（一周）。**对新 App 首发的价值最大** |
| 分批放量 | ⭐⭐ 中 | 若服务端分桶，可按比例开功能；但苹果 TestFlight / Phased Release 已覆盖大部分场景 |
| 运营开关 | ⭐ 低 | 视业务而定 |
| AB 实验 | ⭐ 低 | 你有独立 Tagging 方案，通常实验平台自己管理 |

**建议**：不要为此单独搭一套。优先级是

1. **先确认现有原生壳里有没有** —— 大概率有（壳通常自带配置下发），直接复用
2. 用服务端已有的配置通道下发一个简单的 `feature_flags` JSON
3. 只有在都没有时才新建，且**用平台 a 而不是自己造**

> **一个容易忽略的点**：新 App 首发后如果发现严重问题，你没有旧版可回滚（App Store 不支持降版本）。所以 **Kill switch 是首发期唯一的急刹车**，这一条别省。

## 3. 补充 4 重新定性：从"本地数据迁移"到"身份连续性"

本地数据不用迁了（删掉整章）。但**服务端侧的连续性**变成新的重点，这部分以前被本地数据问题掩盖了：

| 项 | 要确认的问题 | 不确认的后果 |
|---|---|---|
| **Bundle ID** | 全新上架（新 ID）还是更新那个壳 App（复用 ID）？ | 决定是否需要重新过审、是否要引导用户手动下载、ASO 评分是否归零 |
| **账号 / Token 体系** | 新 App 与壳 App、与 Flutter 内测版，是否共用同一套 SSO？ | 内测用户二次推荐位不一致 → 全员重新登录（可接受，但要提前告知） |
| **服务端 clientType / appVersion** | 新 App 用什么标识请求后端？后端是否按此分分支返回不同结构？ | 灰度期前后端数据结构不一致、解析崩溃 |
| **设备标识 / 推送** | device token 是否重新注册？推送别名/标签体系是否要重建？ | 推送发不到、或给同一设备推两份 |
| **风控设备指纹** | 换 Bundle ID 是否触发风控重判？（新设备 + 新 App = 高风险特征） | 正常用户被拦截 |
| **测试/内测用户数据** | Flutter 内测期间产生的服务端数据是否保留？ | 一般保留，但需确认是否要清理脏数据 |

> 建议 P0 阶段开一次 30 分钟的对齐会，把上面六项一次定死。**这六项不涉及写代码，但每一项返工的代价都是天级。**

## 4. 补充 5：TCA 自动埋点 —— 方案可行，但有四个硬边界

用**高阶 Reducer 拦截 Action 再映射为埋点事件**，这个思路本身是对的，也是 TCA 相对其他架构的独有能力。但它在四个地方会漏：

### 边界 ① Action 粒度 ≠ 事件粒度（重复上报）

一次用户操作常触发 Action 链：`.viewTapped → .submitRequested → .submitStarted → .submitFinished`。Redux 层不理解"这是一个行为"。

**对策**：白名单机制 —— 只有显式列入 `TrackableAction` 的 Action 才上报；配一个 **去重合并窗口**（如 300ms 内同 key 只报一次）。

### 边界 ② Action 里通常缺埋点参数（最麻烦的一个）

Tagging 要的参数往往是业务上下文：商品 ID、来源页、坑位 index、实验分组。Action 里往往没有。

**两个选项，我推荐后者**：

```swift
// ❌ 选项 A：把上下文塞进每个 Action —— Action 定义被埋点需求污染
case submitTapped(itemID: String, source: String, bucket: String)

// ✅ 选项 B：middleware 从 State 快照取上下文
struct TrackingReducer: Reducer {
    func reduce(into state: inout S, action: A) -> Effect<A> {
        if let key = action.trackingKey {
            let ctx = TrackingContext.from(state)   // 从当前 State 抽上下文
            analytics.track(key, ctx)
        }
        return .none
    }
}
```

**代价**：必须在 Spec 里标注"该事件需要哪些上下文字段"，并保证这些字段在 State 中可达。**这条直接反馈到 Screen Spec 模板 —— 埋点节要增加"上下文来源字段"一列。**

### 边界 ③ 曝光（impression）埋点不是 Action 驱动的

列表项"露出 50% 持续 1 秒才算一次曝光"—— 这是 View 层的可见性判定，Redux 层完全看不到。

**必须单列一条独立通道**：SwiftUI 里用 `PreferenceKey` / `onAppear` + 几何可见性计算，或直接把曝光容器做成自建组件（正好接 §5 的自建组件库）。**不要试图塞进 TCA。**

页面停留时长同理。

### 边界 ④ 事件模型需要与 Tagging 文档防漂移

既然 Fernando 侧没上线，**没有历史数据要对齐，这是松绑**。但新的风险是：Tagging 文档改了，代码没跟上。

**对策**：从 Tagging 文档（Excel/JSON/YAML）**生成 Swift 枚举**，CI 里跑 generate + diff。文档是唯一事实源，代码里不允许出现字面量事件名。

另外还要预留：**服务端下发采样率与事件黑名单**（线上发现某事件把日志打爆时能远程关掉）。

## 5. 补充 6：新头号缺口 —— GenUI 与自建组件库的衔接

Figma 权威 + 自建组件优先，这个决策我完全赞成，它比 V1 的裁决规则干净得多。但它引出一个致命前置问题：

### 5.1 GenUI 认不认识你的自建组件？

Figma 里的 `Button/Primary/Large` 是一个 Component 实例。GenUI 从图层生成代码时，**通常不会自动知道它对应你已经写好的 SwiftUI `DSButton`** —— 它会把 Component 展开成一堆原始图层（`RoundedRectangle` + `Text` + padding），生成一段重复的、不复用组件的死代码。

**这会让 GenUI 的价值从"生成页面"降级为"生成页面周边的一次性代码"，而且每改一次设计稿就全部失效。**

必须在 P0 做一次 **GenUI 组件映射 POC**：

| 验证项 | 方法 | 通过标准 |
|---|---|---|
| 是否支持 Component → 已有 SwiftUI View 的映射 | 拿 3 个代表组件试：按钮 / 卡片 / 列表项 | 生成代码里出现 `DSButton(...)` 而不是展开图层 |
| 映射表能否版本化、能否 CI 校验 | 导出映射配置 | 配置是文件，可 diff |
| 组分 nesting 深度 | 嵌套 Component 能否正确展开 | 两层嵌套不丢 children |
| Figma Variables → Design Token | 改一个 Variable，看 token 是否跟着变 | 单向源成立 |

> 如果 GenUI **不支持**映射：不要放弃它，改为**降级用法** —— GenUI 产出只用于提取"布局意图 + 精确间距/层级"，组件引用由 Agent 做二次替换（把图层块替换成 `DSButton`）。这仍然比从零手写快，但要在工时估算里明确算上这一步。

### 5.2 Figma 组件的变体覆盖率审计（阻塞项）

自建组件库要覆盖组件的全部状态，Figma 里缺 variant 就必定漏<｜hy_place▁holder▁no▁813｜>。P0 必须审计：

```
每个 Figma Component 检查：
  [ ] default        [ ] pressed / highlighted
  [ ] disabled       [ ] loading / busy
  [ ] selected       [ ] error / invalid
  [ ] focused        [ ] 深色模式变体
  [ ] 超长文本       [ ] 无图 / 图加载失败
```

缺的 variant 让设计补。**这份清单的完成度 = 自建组件库能有多完整，也就 = 后期屏幕生产速度快慢。**

### 5.3 由此带来的两个连带好消息

1. **Design Token 的源头变干净了** —— 权威源是 Figma Variables，不是"从 Flutter 反推"。所谓 sticky bot期 bridging 那套（W3C Tokens + Style Dictionary）仍然推荐，但输入侧简化了一半。
2. **视觉回归基准变了** —— 不需要 Flutter golden 了（Flutter 不是视觉准绳）。改为 **Figma 导出切图 ↔ SwiftUI snapshot**。少了一整套 double-run 成本。Flutter 真机截图仍值得留，但只作为**流程与交互**参考。

### 5.4 仍然保留的一条：行为逻辑以 Dart 为准

Figma 不描述行为。**Screen Spec 里的"视觉节"来自 Figma，"行为节"来自 Dart**，这个分工要写进 Spec 模板并在 Agent prompt 里点明。

## 6. 补充 1 与 2 带来的新缺口

### 6.1 原生壳的可继承度体检（新增阻塞项）

"复用壳"听起来省事，但壳自带的技术债会顺着污染新项目。P0 必须做一次**可继承度矩阵**：

| 壳的能力 | 复用 | 替换 | Facade 包装 | 需确认的问题 |
|---|---|---|---|---|
| 网络层 / 拦截器 / Token 刷新 | | | | 与 Domain SDK 是否打架？两套刷新逻辑必炸 |
| 账号 / 登录态 | | | | 与 Flutter 版是否同一套 SSO |
| 埋点 SDK | | | | 能否承载新 Tagging 方案 |
| 配置下发（即 §2 的远端开关） | | | | 有没有现成的？有就直接用 |
| 崩溃 / 性能监控 | | | | 符号表、版本串是否分开 |
| 推送 | | | | §3 的设备标识问题 |
| CI / 打包 / 证书 | | | | 最有价值的一项，通常直接复用 |
| 部署 target | | | | **壳若是 iOS 13，与 iOS 16 目标冲突时需处理** |
| Xcode / Swift 版本 | | | | TCA 用宏 → 需 Xcode 15+；Swift 6 language mode 能否开 |

**判断口径**：越是"横切 infra"（CI、监控、配置下发）越值得直接复用；越是"业务 infra"（网络、账号、路由）越要评估，因为新项目要重新定义它们的边界。

### 6.2 iOS 16 基线的连锁决策（技术约束，必须现在算清）

`NavigationStack` 是 iOS 16+，没问题。但 iOS 16 意味着**一整批 iOS 17 的现代 API 全部失效**，这不是小事：

| iOS 17+ 但用不了 | 替代方案 | 影响面 |
|---|---|---|
| `@Observable` 宏 | `ObservableObject` + `@Published` | **全项目**：粒度变粗，无效重绘增多，要更注意 View 拆分 |
| TCA `@ObservableState`（依赖 Perception 回移植） | `ObservableObject` 模式 / `WithPerceptionTracking` | TCA 仍可用，但样板多一点，**必须在 P3 试点先验证** |
| `SwiftData` | Core Data / GRDB / SQLite.swift / 文件缓存 | **持久化方案需重定** |
| `ContentUnavailableView` | 自建空态组件 | → 走 §5 自建组件库，正好覆盖 |
| `.scrollPosition(id:)` / scrollTarget | `ScrollViewReader` 手动算 | 滚动定位、分页吸顶等要手写 |
| `onChange(of:initial:)` 双参 | `onAppear` 手动补首次 | 小坑，容易漏 |

**iOS 16 也不是全是坏消息**，以下几样可用，值得在方案里明确利用：`Charts`（原生图表，若 Flutter 有自绘图表可大幅简化）、`Layout` 协议、`AnyLayout`、`ViewThatFits`、`Grid`、`ShareLink`、`PhotosPicker`、`Gauge`。

**决策口径**：iOS 16 这个决定本身要**数据驱动**。Flutter 版目前支持的最低 iOS 版本是多少？现有内测/目标用户的 iOS 版本分布是什么？如果 Flutter 版当前支持 iOS 12，那 iOS 12–15 的用户占比可能有个位数到十几个百分点。**这个数要拿到，让老板签字，不要默认。**

### 6.3 自定义路由层的隐藏复杂度

自建 NavigationStack 路由时，以下五项是 Easy-to-miss 的：

1. **NavigationPath 的 Codable 一致性** —— 若做路由栈持久化/深链重建，枚举 case 改名或加字段后，旧用户存的 path 解码失败会崩。必须给每个路由加**版本号**，解码失败时安全降级到首页。
2. **深链外部入口** —— Universal Link 冷启动时要一次性重建整条路由栈，这是最常见的线上崩溃点。
3. **返回值传递** —— SwiftUI 没有 delegate，通常用 `@Binding`/`Dismiss` 或路径回调，要在 Spec 的"导航节"明确。
4. **路由守卫** —— 未登录拦截要在路由层统一做，不要每个屏自己写。
5. **返回手势与 swipe-back 的自定义** —— 若做了自定义导航栏，interactivePop 手势容易失效或卡死。

### 6.4 UIKit 逃逸通道要预留

纯 SwiftUI 不代表没有 UIKit。复杂自定义转场、高性能长列表、地图/相机/网页容器、某些三方 UI SDK，仍需 `UIViewRepresentable`。**架构上要预留这个槽位**，不要设成"禁止 UIKit"，否则到后期会以很丑的方式打破规则。

## 7. 修订后的落地路线图

| Phase | 内容 | 关键产出 | 门禁 |
|---|---|---|---|
| **P0 定性** (1–2w) | ① iOS 版本分布数据 + **target 签字** ② **原生壳可继承度矩阵** ③ **Bundle ID / 发布策略 / 服务端标识六项对齐** ④ **GenUI 组件映射 POC（3 组件）** ⑤ **Figma 组件 variant 覆盖率审计** ⑥ Flutter 组件与风险扫描 ⑦ Tagging 文档冻结 → 生成 Swift 枚举 ⑧ Dart 逻辑提取（可延后） | `PLAN_V2.md` + 决策记录 | 工期可估算、POC 有结论 |
| **P1 基础Kit** (3–4w) | DesignKit（Token from Figma Variables + 自建组件库全 variant 覆盖）、RouteKit（含 §6.3 五项）、AnalyticsKit（自动埋点 + 曝光/时长独立通道 + 采样开关）、壳裁剪接线 | 三个 Kit + 演示 App | 组件 100% 有 preview 测试 |
| **P2 Domain SDK** (2–3w，并行 P1) | 七层分层、Mock 实现、与壳网络层的关系定案 | SDK + fixture | 单测覆盖 Mapping / Error |
| **P3 管线试点** (2w) | 3 个代表屏（列表 / 复杂表单 / 自绘或动画）跑完整管线；**实测 GenUI→Layout 净化成本** | 3 个 Feature + 工时基准 + Cheat Sheet | Pipeline 成立，工时可信 |
| **P4 批量生产** | 按 Screen Spec 生产，走 Coverage Checklist | 屏幕池 | 每项三态明确 |
| **P5 发布** | TestFlight 分批放量 + Kill switch 待命 + 崩溃/埋点监控 | 发布包 | 崩溃率 < 阈值 |
| **P6 收尾** | Flutter 仓库转只读归档，保留真机包作参照 | — | — |

**相比 V1 的三处变化**：
- P0 从"扫描"升级为**"决策 + POC"** —— 现在阻塞项全是决策和可行性验证，不是代码量问题
- P1 的 DesignKit **变重**（自建组件库全 variant 覆盖成为硬阻塞），这是 Figma 权威路线的代价
- V1 的"灰度/双跑"阶段删除，替换为 TestFlight 分批 + Kill switch
