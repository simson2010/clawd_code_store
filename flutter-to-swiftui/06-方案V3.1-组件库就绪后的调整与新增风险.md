# 方案 V3.1：组件库就绪后的调整与新增风险

> 承接 V3（`方案V3_终版落地计划.md`）。本文只写**因「组件库完备且线上在用」而变化的部分**，其余以 V3 为准。

---

## 0. 一句话

这是本项目目前为止最大的一个去风险事件：P1 的硬阻塞消失，工期可压缩约 2–3 周。

**但请注意性质变化**：风险没有消失，而是**从「建设风险」换成了「依赖风险」**。

- 建设风险：看得见、可加班解决、在你们团队内部
- 依赖风险：**看不见、加班解决不了、优先级不在你们手上**

它需要的是完全不同的治理手段 —— 版本锁定、回归门禁、跨团队 SLA。这套东西现在就要建，不能等到第一次踩坑。

---

## 1. 直接被消灭的问题

| 原议题 | 原状态 | 现状 |
|---|---|---|
| V3 G6：SwiftUI 组件库完备度 | **P1 硬阻塞、最大未知数** | ✅ 消除 |
| V2 §5.1：GenUI 组件映射 POC | 高风险前置项 | ✅ 降为常规验收 |

**工期影响**：P0 可从 2 周压到 1 周，P1 可从 3–4 周压到约 2 周。合计省约 2–3 周。

## 2. 新增的六项风险（共享依赖的代价）

### 风险 R1：版本升级的连带破坏

库会为**其他 App 的需求**演进。某次升级可能无声地改掉你 App 里的视觉或交互。

| | |
|---|---|
| **表现** | 升级后某屏样式变了、某组件多了个动画、间距微调 |
| **对策** | ① 锁版本 + 显式升级（禁止跟随 main）② **每次升级跑组件的 snapshot 回归** ③ 订阅 changelog 并纳入发版评审 |

> 如果组件库有 **preview catalog / 组件目录 Demo App**，直接拿它做 snapshot baseline，成本很低。**这一项建议在 P1 就建好**，否则每次升级都是盲升。

### 风险 R2：需求排队（你的 variant 缺口在别人的节奏里）

组件库"完备"是对现有 App 完备。**你的 Flutter App 未必被覆盖到。**

| | |
|---|---|
| **表现** | 某个组合（如「带副标题 + 右侧徽标 + 加载态」）库里没有 |
| **对策** | P0 立即产出**缺口清单**，尽早提需求排期。**越晚提，越容易卡在 P4 批量生产期** |

一条硬规则要先定：**本地不允许 fork 组件库**。优先级依次是 —— 扩展配置 → 向库提需求 → 本地做一层薄包装。这一条要写进开发规范，否则一旦有人 fork，版本治理立刻失效。

### 风险 R3：双平台一致性约束

既然是双平台组件，就意味着「只改 iOS 侧」通常不被允许。

| | |
|---|---|
| **好处** | 两体验自动一致，不用单独维护 iOS HIG 特化 |
| **代价** | 当你确实需要 iOS 特有行为（系统分享、长按菜单、Haptic 细节、原生导航栏语义）时会受阻 |
| **对策** | P0 盘点「本项目需要的 iOS 特化点」，能交给组件库内置最好；不能的，在 App 侧做**薄适配层**（这正是 V1 就提过的 App 级组件契约），不要在业务页裸调库组件 |

> 这条与 V1 的「App 级组件适配层」建议完全吻合 —— 有了共享库，这层适配的价值反而**更高**：它是你唯一能自主演进、不受库影响的地方。

### 风险 R4：覆盖率 ≠ 你的 App 够用

重点查三类：

1. **Flutter 端有但库里没有的自定义视觉**（尤其是自绘、图表、特殊卡片）
2. **库里有但 Flutter 端用法不同的**（同名不同义）
3. **组合型布局**（库提供砖块，但整体的复合容器需要自建）

第 2 类最危险：名字一样所以大家都以为对齐了，实际语义不同，要到测试后期才发现。

### 风险 R5：既定使用规范的服从成本

已有 App 在用 = 已有既定用法。这些很可能包含：**TCA 集成方式、依赖注册 (@Dependency) 方式、错误处理约定、测试写法、目录结构**。

**对策**：不要另起一套。去把它们的规范抄过来，做成：
- 给 Agent 的**硬约束列表**（"必须照内部 Feature 的写法"）
- 给 Reviewer Agent 的**检查项**

### 风险 R6：Bug 修复的 SLA 不在你手上

组件 bug 要跨团队修，优先级由对方排。

| | |
|---|---|
| **对策** | ① P0 就建立协作机制与升级路径（谁是对口人、多久响应）② App 侧预留 **hotfix 包装能力**（在适配层临时打补丁，不等库发版）③ 把你依赖的高风险组件列出来，作为对方的重点保障对象 |

第 ② 条是 R3 里那个 App 级适配层的又一个收益 —— **它是你的应急阀门**。

## 3. 一个被严重低估的加速机会：线上 App 是最好的语料库

这一点建议你重点看下，它的性价比可能高于本文其他所有内容。

**已经有线上 App 用这套组件 + 这套 TCA 规范在跑** —— 意味着你们公司里已经存在**几十个甚至上百个符合规范的 Feature 实现**。这是 AI Agent 最好的 few-shot 素材：

| 做法 | 收益 |
|---|---|
| 抽取 20–30 个内部 Feature 建成 **"Golden Examples" 语料库** | Agent 填 Reducer 时照着写，而不是自由发挥 |
| 从中提炼**命名约定、Effect 写法、错误处理范式、依赖注册、测试写法** | 直接变成 Agent prompt 的硬约束 |
| 把内部已有 **lint / 架构规则**接入 Reviewer Agent | 自动校验，减少人工 review 负担 |
| 拿其中带测试的 Feature 生成 **`TestStore` 测试范式** | 补齐 V3 §8 要求的 Reducer 单测， Agent 可直接照抄结构 |

**为什么这很重要**：之前方案里最大的不确定性是"Agent 生成的 Reducer 逻辑质量到底如何"。有了内部范式，**这个不确定性大幅下降** —— Agent 从"创作"变成了"模仿"，而模仿正是它最擅长的。

> **行动建议**：P0 第一周就做这件事（1 人 3 天即可），产出 `GoldenExamples/` 目录 + 一份 `AGENT_RULES.md`。这是整条产线里 ROI 最高的一项投入。

## 4. 前提：不要因为好消息而跳过隔离机制

**组件库再好，也不解决 V3 §2 的「GenUI 再生 vs 手写隔离」问题。**

那是 GenUI 的输出格式与你们手写逻辑之间的关系问题，与组件库完备与否无关。它仍然是 **V3.1 的头号工程风险**，仍然要在 P1 验收。

重申 P1 的出口标准（不变）：

> **改一次设计稿 → 重新 GenUI 生成 → 业务逻辑不丢。**

这条不过，不许进 P4 批量生产。

## 5. 立刻要确认的十项（1 周内）

| # | 确认项 | 为什么重要 |
|---|---|---|
| 1 | 依赖接入方式（SPM / CocoaPods / monorepo） | 影响 CI 与 GenUI 产物形态 |
| 2 | **组件库的 iOS 部署 target** | 若它要求 iOS 17，与你的 iOS 16 目标**直接冲突** |
| 3 | 是否 Swift 6 / Sendable ready | 与网络库那条同源，决定能否开 Swift 6 mode |
| 4 | 是否已提供 TCA 适配（可观察/绑定封装） | GenUI 绑定 TCA 说明大概率有，需确认形态 |
| 5 | **版本发布节奏、changelog、升级政策** | R1 的治理基础 |
| 6 | 提需求的流程与实际 SLA | R2/R6 的预期管理 |
| 7 | **是否有 preview catalog / Demo App** | 有则免费得到 snapshot baseline |
| 8 | Token 的输入源（Figma Variables？独立仓库？） | 决定能不能直接复用，别重复建 |
| 9 | 深色 / Dynamic Type / RTL / VoiceOver 覆盖情况 | 这些如果库已内置，P4 省一大块 |
| 10 | **能否读到其它线上 App 的源码** | §3 语料库的前提，**这项要尽早开口** |

> 第 2 项请优先确认 —— 这是唯一一条「可能推翻技术选型」的信息。

## 6. 修订后的 P0 / P1

### P0（1 周，压缩前 2 周）

只做**验证与确认**，不写生产代码：

1. §5 十项确认（**其中第 2 项最优先**）
2. **缺口清单**：拿 Flutter 版视觉 / Figma 逐屏对组件库，产出「库有 / 库缺 / 语义不同」三态表（半天到一天，库已成熟所以很快）
3. **搭 `GoldenExamples/` 语料库**（§3，最高 ROI）
4. 确认 GenUI Figma 覆盖矩阵
5. 定再生/手写隔离方案（要拿到 GenUI 团队的配合承诺）
6. 迁移数据清单经产品确认（V3 §6.2）

### P1（约 2 周，压缩前 3–4 周）

1. 组件库接入 + Token 打通
2. **App 级组件适配层**落地（同时作为 R3 iOS 特化点与 R6 应急阀门）
3. 隔离机制落地 + CI 守护
4. **snapshot baseline 建立**（源自组件库 Demo 或现有 App）
5. **2 屏端到端跑通，含一次设计改稿验证隔离有效**

## 8. 一句话总结

组件库就绪把最大的一块石头搬开了，**但它换来的是一类需要「治理」而不是「加班」来解决的问题**：版本锁定、升级回归、缺口提需排队、跨团队 SLA。这几件事都必须在 P0/P1 建好，因为它们的成本是**后置且复利**的 —— 现在不建，每一次组件库升级都要付一次学费。

而眼前最高性价比的一件事，是**把现有线上 App 的 Feature 实现变成 Agent 的语料库**（P0 第 3 项，1 人 3 天）—— 它直接降低整条产线最大的不确定性。
